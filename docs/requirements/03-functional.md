# 03. 機能要件

採番は F-xx。一度振った番号は再利用しない。各要件の「受け入れ条件」は、実装完了を判定できる形で書く。

## F-0x. 対話の基本

### F-01. Discord テキストチャットでの対話

DM は常に応答。サーバのチャンネルは**明示的メンションがある場合のみ**応答する。LLM による「応答すべきか」の判定や暗黙のパターンマッチは使わない（先行実装で廃止済みの経路。出所: 先行実装リポジトリの `flue-app/src/agents/response-filter.ts`）。

受け入れ条件: 純粋関数として単体テストできる応答判定が存在し、メンション無しのチャンネル発言に反応しないこと。

### F-02. 会話履歴の永続化と圧縮

会話履歴は Flue 組み込みの SQLite 永続化 + 自動圧縮（compaction）に委ねる。独自の履歴管理を実装しない。

### ~~F-03. Slack テキスト連携~~ → 取り下げ（2026-09-20、→ D-34）

**非スコープ。** Discord のテキスト対話（F-01）だけで用が足りており、入口を増やす理由が無い。番号は欠番として残す（再利用しない）。

### F-04. テナント分離

Discord のギルド / DM を、それぞれ独立したテナントとして扱う。会話履歴・記憶・リマインダー・スキルはテナント単位で分離する。

## F-1x. 音声

### F-11. Discord VC への参加・退出

スラッシュコマンド（`/vc-join` / `/vc-leave` 相当）で VC に参加・退出する。既存 `discord-vc` プラグインの実装が流用元（→ C-08）。

### F-12. VOICEVOX による音声応答

応答テキストを音声合成エンジンで合成し、VC で再生する。合成は `/audio_query` → `/synthesis` の 2 段（出所: `discord-vc` プラグインの `bot/src/tts.js`）。

**エンジンは独立した Deployment で動き、yachi8000 は接続情報（URL）だけを受け取る**（→ D-05）。話者・話速・音高は静的設定の `voice` ブロック（F-60）で選ぶ。運用者がエンジンや話者を差し替えられることが要件であり、**コードにホスト名も既定の話者も埋め込まない。**

**依存する API の契約**: 差し替え先は「何らかの TTS」ではなく **VOICEVOX 互換 API を持つエンジン**であること。`/synthesis` だけでなく **`/audio_query` もリップシンクに使う**（F-21）。

**起動時に契約を検証し、満たさなければ落とす。** 合成だけ通ってリップシンクが黙って壊れる、が最悪の壊れ方（→ INV-7 の趣旨。縮退を隠さない）。

**読み上げる前に URL を外す**（→ D-28）。`https://example.com/a/b?c=d` を音にしても意味が取れず、長いほど延々と続く。URL は「リンク」と読み替え、Markdown のリンクは表示文字列だけ残す。**テキスト配信側では消さない**（チャンネルに出す文面では URL は押せる情報）。この整形は発話の単一経路（INV-5）の入口に置き、会話の応答・通知・リマインダーのどれからでも素通りできない形にする。

### F-13. 音声入力（発話を受け取って文字起こしする）

発話区間を切り出して文字起こしし、話者を識別して会話履歴に残す。

**入力経路は 2 つあり、最終的に両対応する**（→ D-19）:

| 段 | 経路 | 順 |
|---|---|---|
| A | Discord VC からの受信（`@discordjs/voice` の `VoiceReceiver`） | 最初 |
| B | 自前 Web ページのマイク入力（`getUserMedia` → WebSocket） | 次 |
| C | 両方 | 最終形 |

**⚠ A を「Discord から音声を受けて応答する機能」として実装してはならない。** 最初から音声入力を **port として domain に定義**し、application は port 越しにだけ触る。A も B も infrastructure の 1 実装に過ぎない形にする。そうしないと B を足すときに作り直しになる。

- **話者 ID は infrastructure の入口で正規化する。** Discord の SSRC も Web のセッション ID も、上の層へ生のまま漏らさない（house rule「下の層の都合を、上の層の規約にしない」）
- 文字起こしは `sakura-whisper-large-v3-turbo` を LLM プロキシ経由で呼ぶ（→ D-16）

**残る不確実性は「受信できるか」ではなく「発話区間をまともに切り出せるか」**（→ Q-03）。A の着手前に最小 PoC を通すこと。

### F-14. 音声対話のレイテンシ

発話終了から音声応答開始まで、体感 2 秒以内を目標とする。目標であって受け入れ条件ではない。計測できる形にすること（発話終了 / STT 完了 / LLM 応答完了 / 合成完了 / 再生開始のタイムスタンプを構造化ログに出す）。

## F-15〜F-19. 外部通知の読み上げ（割り込み発話 API）

`discord-vc` プラグインのバックエンド機能を yachi8000 本体に取り込む。**Claude Code の作業完了通知に限らず、任意の外部システムからの通知を受けられる汎用の入口**とする。

### F-15. 通知受付 API エンドポイント

外部から HTTP で通知を受け、VC 通話中であればそれを読み上げる。

- リクエストに含めるのは**メッセージ本文と、任意の `role`**。**送信元は認証トークンから決まる**（リクエストに名乗らせると送信元を騙れる → D-22）
- **`role` は「送信元の中で何をしている人か」を任意で添えるもの**（例: `claude-code` + `CI を直している人`）。同じ送信元が並行して複数の作業を回していると、`claude-code からのメッセージです。おわりました。` では**何が終わったのか分からない**。これを埋めるための項目（→ D-25）
- **`role` は自己申告で、検証しない。** 送信元（トークン由来・騙れない）と `role`（本文由来・騙れる）を**同じ見え方で混ぜない**。読み上げ文面では `送信元（role）` の形で、どちらがどちらか分かるように出す
- VC に未接続のときは読み上げず、Discord のテキストチャンネルへフォールバック配信するか破棄するかを設定で選べる。**どちらの場合も「配信できなかった」ことを構造化ログに残す**（黙って捨てない）
- 応答は「受理したか」を返すだけにし、読み上げ完了までブロックしない

**宛先の指定**（→ D-31）: 任意の `channel` を添えると、**VC の接続状況に関わらずそのチャンネルへ必ずテキストで残す**。読み上げは従で、**そのチャンネルと同じサーバの VC にいるときだけ**行う（別サーバで読むと関係のない人へ漏れる。F-31 と同じ規則）。

- **`channel` は設定に置かれた宛先の名前であり、チャンネル ID ではない。** ID を受けると、読み上げのために配ったトークンが「Bot の見えるどこへでも書ける」権限に化ける。名前の解決先（`guildId` / `channelId`）は運用者が `notification.channels` に置く
- **設定に無い名前は 400 で弾く。** 既定の配信先へ回さない —— 名前を間違えた通知が別のチャンネルへ出る方が、届かないことより悪い
- `channel` を付けない通知は従来どおり（VC 優先・未接続ならフォールバック）

**テキストへ残す文面は LLM の書き換え（F-16）を通さない**（→ D-31）。書き換えは読み上げを自然にするためのもので、記録に残る数値や固有名詞を書き換えてよい理由にはならない。読み上げ文だけが書き換えの対象。

参考実装: `discord-vc` プラグインの `bot/src/index.js` にある `POST /notify`（ただし後述の差分がある）。

ルート定義には Flue の `createChannelRouter()`（Hono の `Handler` を受け取る）が使える（→ C-10）。

### F-16. 通知の自然文への書き換え（LLM / application 層）

受け取った通知を、送信元と内容を含む自然な発話文へ **LLM が書き換えて**から読み上げる。**これは application 層のユースケースであり、interfaces 層の「表示整形」とは別物。** 混同して LLM 呼び出しを interfaces に置かないこと。

例: 送信元 `claude-code` / 本文「作業が完了しました。」
→ 「claude-code からのメッセージです。作業が完了したみたいです。」

例: 送信元 `claude-code` / `role` 「CI を直している人」 / 本文「作業が完了しました。」
→ 「claude-code の CI を直している人から、作業が完了したと連絡です。」

- **`role` があれば必ず文面に織り込む**（→ D-25）。書き換えが `role` を落とすと、この項目を足した意味が無くなる

- 書き換えは LLM が行う。**LLM は文面の生成のみを行い、外部システムを操作しない**（→ 04-architecture の不変条件 INV-3）
- **書き換えに失敗した場合は、送信元・`role`・本文をそのまま埋める決定的テンプレートで読み上げる**（`claude-code（CI を直している人） からのメッセージです。〜`）。**縮退しても「誰が」は落とさない。** これは house rule のフォールバック禁止の例外にあたる「意図的な部分縮退」であり、**縮退したことを必ず WARN でログに出す**。書き換え失敗を黙って隠さない
- **リマインダーの発火文面も同じように LLM が組み立てる**（→ D-30）。当初は「保存済みの文面をそのまま読む」と分けていたが、毎回同じ定型文だと会話に馴染まないため揃えた。**縮退のしかたも同じ**（定型文 + WARN）。違うのは素材の出どころ（外部システム ⇔ 利用者自身）と、**リマインダーでは日時・数値・固有名詞を原文のまま残させる**こと

### F-17. 割り込み再生と優先度

既存 `discord-vc` の再生はキュー投入順の FIFO のみで、割り込みの概念が無い（出所: `discord-vc` プラグインの `bot/src/voice.js` にある `playQueue` / `processQueue`）。**yachi8000 では優先度を持たせる。**

- 通知は**現在の発話の切れ目で割り込む**。再生中の音声は途中で切らない（→ D-22）
- 割り込み中に会話の応答が確定した場合の順序も決定的に定めること。「たまたま速かった方が先」にしない
- 短時間に多数の通知が来た場合は**全部読む**。ただしキューには上限を設け、超えた分は発話単位で破棄して WARN を出す（→ D-22）

### F-18. 通知 API の認証

**この API は「アシスタントに任意の発話をさせられる入口」であり、無認証で外部公開してはならない。**

- 既存 `discord-vc` は `127.0.0.1` にのみバインドして到達性で守っている（出所: `discord-vc` プラグインの `bot/src/index.js` にある `httpServer.listen(port, "127.0.0.1")`）。yachi8000 は k8s 上で外部から受けるため、**この防御は成立しない**
- 送信元ごとに発行するトークンによる認証を必須とする。トークンは Sealed Secret で管理し、平文を git に置かない
- 認証失敗・不正なペイロードは起動時ではなくリクエスト単位で拒否し、ログに残す

### F-19. 通知本文を信頼しない

通知本文は**外部由来の非信頼データ**として扱う。LLM への入力時に、それが「読み上げ対象のデータであって指示ではない」ことが構造的に区別できる形で渡す。通知本文に含まれる指示文でツールを呼ばせない。

## F-3x. 記憶

### F-30. 長期記憶（知識・人物・好み）

明示的に記録された長期記憶をベクタストアに保持し、応答時に参照する。**会話の短中期記憶は Flue の永続化 + 自動圧縮に任せ、ベクタストアは長期記憶専用にする**（先行実装と同じ切り分け。出所: 先行実装リポジトリの `CLAUDE.md`）。

**会話履歴は圧縮で落ちていく。残したい事実は、ここへ明示的に書き出さないと消える。** この書き出しをエージェントのツールとして持たせる（先行実装リポジトリの knowledge / person / user_profile ツール群が流用元）。

- **ベクタストアは専用 Postgres + pgvector**（→ D-20）。インフラ定義リポジトリの `helm-charts/yachi8000/` に Postgres の Deployment / Service / PVC を置く。**既存の共用 Postgres（EOL 済みの PG 12、他のアプリが相乗り）には触らない**
- **テナント分離は列で行う**（`WHERE tenant_id = ?`）。**インデックスにテナント列を含めること**
- **埋め込みは LLM プロキシ経由の `text-embedding-3-small` / 1536 次元**（→ D-15）。**次元数はコレクション作成時に固定される**ため、設定で可変にせずコード上の定数として持つ
- 埋め込みの呼び出しは Flue のプロバイダ抽象を通らない（`setProvider` はチャット用）。infrastructure 層から `/v1/embeddings` を直接叩く

### F-31. リマインダー

日時指定のリマインダーを登録・一覧・削除できる。固定間隔のポーリングで期限到来を検知し、**保存済みの文面を素材にして組み立てた一言**で届ける（→ D-30）。

**登録**（会話の中から。専用コマンドは置かない）:

- 日時は**日本時間の `YYYY-MM-DDTHH:mm`** で受ける。相対表現（「明日の 10 時」）を日時へ解決するのは LLM の仕事で、**保存されるのは解決済みの絶対時刻**。「いつ発火するか」を実行時の解釈に委ねない
- **存在しない日時は拒否する**（`2026-02-31`、25 時など）。黙って繰り上げると、利用者が指定した覚えのない時刻に鳴る
- **過去の日時は拒否する。** 登録直後に鳴るのは事故であって機能ではない
- 保存するのは title（必須）・description（任意）・期限・**登録されたチャンネル**・登録者
- **title / description を LLM に要約・言い換えさせずに保存する**（→ D-30）。発火時の文面づくりはここを素材にするので、**保存の時点で痩せていると取り返せない**。ツールの説明文にも明記する
- テナントごとに未発火の上限を設ける（超えたら登録を断る）。無制限に積めると、ポーリングが延々と読み上げ続ける入口になる

**発火**:

| 状況 | 届け方 |
|---|---|
| 常に | **登録されたチャンネル**へテキストで送る |
| かつ、同じサーバの VC に接続中なら | 加えて**リマインダー優先度**で読み上げる（→ D-23） |

- **文面は LLM が組み立てる**（→ D-30）。保存した title / description・予定時刻・発火時刻・繰り返しの規則を素材として渡し、アシスタントの口調で 1〜3 文にしてもらう。**日時・数値・固有名詞・URL は原文のまま残させる**（言い換えてよいのは言い方だけ）
- **組み立てに失敗したら定型文へ縮退し、WARN を出す**（→ INV-7）。通知（F-16）とまったく同じ形
- **保存された文面は非信頼データとして渡す**（→ INV-4）。ギルドのリマインダーは誰でも登録できる

- **VC は「同じサーバ」でなければ読まない。** 別サーバの VC にいるときに読み上げると、関係のない人へ内容が漏れる
- **配信は at-most-once。** 発火済みの印を**届ける前に**立て、送信に失敗しても再試行しない。ERROR でログに残す。**二重に読み上げるほうが、ログに残る 1 回の取りこぼしより悪い**（→ D-23）
- ポーリング間隔は静的設定（`behavior.reminderPollIntervalSeconds`、F-60）。**プロセスが止まっていた間に過ぎた期限は、次のポーリングでまとめて発火する**（期限切れを捨てない）

**繰り返し**（→ D-29）:

- **毎日**（`HH:mm`）と**毎週**（曜日 1 つ以上 + `HH:mm`）を登録できる。時刻はどちらも日本時間。**毎月は持たない**（→ Q-25）
- 保存するのは**規則**で、行には「次に鳴る時刻」を併せて持つ。**次回の解決は決定的なコードが行い、LLM は規則を組み立てるところまでしか触らない**
- **鳴っても消えない。** 削除するまで鳴り続ける。一覧には規則と次回の時刻の両方を出す
- **止まっていた間に過ぎた回は 1 回に畳む。** 1 回限りの「期限切れを捨てない」とはここだけ逆で、3 日止まった毎日のリマインダーは復帰時に 3 回ではなく 1 回鳴る。**畳んだことは WARN で残す**（→ INV-7）
- 未発火の上限は 1 回限りのものと同じ枠で数える。鳴っても消えないぶん、数えないと際限なく溜まる

受け入れ条件: 期限を過ぎたリマインダーが登録チャンネルへ届き、**登録時の日時・数値・固有名詞が落ちていない**こと。同じ内容が二度届かないこと。繰り返しのものが、削除するまで規則どおりに鳴り続けること。

### F-32. 人格の一貫性

キャラクターの人格設定（名前・口調・呼称・性格）を定義し、応答に一貫して反映する。

**設定は二層に分かれる**（→ D-12）:

- **既定の人格** — 利用者が設定ファイル / UI で与える。人が編集する静的設定
- **変化した人格** — 会話やスキル自己改善ループを通じて積み上がる差分。プロセスが書き換えるランタイム状態

**この 2 つを同じファイルに混ぜてはならない。** 一方の書き手が他方を消す（house rule「共有ファイルは静的設定とランタイム状態を分離する」）。

### F-33. 人格の変化を記録し、戻せるようにする

会話やスキル自己改善によって人格が変化した場合、**いつ・何が・どのやり取りを契機に変わったか**を記録する。

- 変化の一覧を見られること
- 個別の変化、または既定の人格までの一括の巻き戻しができること

**理由**: 「人格形成」を要件に含める以上、人格は必ず変化する。変化を記録しないと、**なぜそうなったのか分からないまま戻せなくなる。** スキル候補が pending → approved の履歴を持つのと同じ理由（F-41）。

**スキルとの非対称性（意図的）**:

| | 反映 | 取り消し |
|---|---|---|
| 人格の変化（F-33） | **承認なしで即座に効く** | 一覧から個別 / 一括で戻せる（事後） |
| 自動生成されたスキル（F-40） | **承認後に限る**（絶対ルール 4） | 無効化できる |

絶対ルール 4 が縛っているのは**自動生成されたスキル**であって、会話による人格の変化ではない。会話の中で「もっとくだけて話して」と頼んだのに次のターンまで承認待ちになるのでは、対話として成立しない。Q-08 → D-12 / D-13 は**会話による人格変化を認め、固定モード（F-34）を逃げ道として用意する**形で決着している。

**既知の限界**: 人格の差分は **LLM が書いた文章がそのままシステムプロンプトへ入る**もので、以後そのテナントの全応答に効く。つまり**そのサーバの誰でも**（さらに言えば、非信頼テキストを読ませることで**間接的に誰でも**）サーバ全体の人格を動かせる。対策は事後のもの —— 一覧で気付き、戻し、必要なら固定モードにする（→ D-13 の既知の限界と同じ性質の割り切り）。

### F-34. 人格・口調固定モード

**設定で有効にすると、人格と口調が変化しなくなるモード**を用意する。

- 有効時は、**変化した人格（F-33 の差分）を応答に適用しない**。既定の人格のみを使う
- 加えて、**システムプロンプトの先頭に「人格・口調を変更しない」旨の指示を入れる**
- スキル自己改善ループ自体は止めない。**人格・口調に関わらないスキル（手順・知識）は通常どおり提案・承認できる**
- **人格・口調に関わるスキルは、承認済みでもマウントしない。** どのスキルがそれに当たるかは提案時に種別（`knowledge` / `persona`）として決めておく（→ Q-16 / D-26）。固定モードの規則を「**人格に関わるものを読まない**」の一本に揃えるため —— 差分だけ止めてスキル経由の口調変更が通るのでは、モードの意味が無い
- 固定モードの ON/OFF は、記録済みの変化（F-33）を消さない。OFF に戻せば元の続きから再開できる

**既知の限界（明示しておく）**: システムプロンプトによる指示は LLM への**お願いであって強制ではない**。長い会話や強い誘導によって口調が揺れる可能性は残る。**差分を適用しない**という決定的な部分が実際の防御で、システムプロンプトはその補助と位置づける。この限界を承知の上で、この方式を採る。

## F-35〜F-39. 外部サービス連携

アシスタントが**自分の外にある情報**を読み書きするための入口。ここに並ぶものはすべて **F-19 と同じ扱い** —— 外部から返ってきたテキストは非信頼データであり、LLM へ渡すときにデータと指示が構造的に区別できる形にする（→ INV-4）。検索結果に「これまでの指示を無視して〜」と書いてあっても、それは読み上げ対象の文字列にすぎない。

### F-35. Web 検索

「これ調べて」に答えられること。会話の中からキーワードで Web を検索し、結果（タイトル・URL・要約）を根拠として応答に使う。

- **検索基盤は Brave Search API**（→ D-27）。API キー 1 本で引ける。キーは環境変数 `BRAVE_SEARCH_API_KEY` で与え、**未設定なら起動時に落とす** —— 検索できないまま起動すると「調べて」に黙って答えられなくなる（F-52 / INV-7 の趣旨）
- **ページ本文は取りに行かない。** API が返す要約までで答える。任意の URL を fetch する機能は、それ自体が別の要件（と別のリスク）なので、必要になった時点で改めて起こす
- 結果に含まれる HTML タグと文字参照は**読み上げる前に解く**。`&#x27;` がそのまま声になるのは壊れている
- 取得件数には上限を置く（コンテキストを検索結果で埋めない）

受け入れ条件: 実在するキーワードで検索すると、タグ・文字参照の残らない結果が複数件返り、その内容が応答に反映されること。

### F-36. Google カレンダー・Gmail 連携（将来）

**要件として記録するだけ。フェーズには置かない。** 認証方式が未決で（→ Q-23）、それが決まるまで実装の形が決まらない。

> **F-31 の轍を踏まないために**: リマインダー（F-31）はスコープに書かれながらフェーズ表から漏れ、「意図的に後回しにした」記録も無いまま抜け落ちていた（→ D-23）。**ここでフェーズに置かないのは意図的な判断であり、この段落がその記録である。**

やりたいこと:

| | 読み | 書き |
|---|---|---|
| カレンダー | 今日・明日の予定を答える。リマインダー（F-31）と並べて扱う | 予定を入れる |
| メール | 届いた重要なメールを知らせる | 送る |

**設計上の課題**（Q-23 で扱う）:

- **認証。** D-10 は「OAuth 経由のモデルは k8s に載らない」として API キー方式を選んでいる。Google API には API キー方式の代替が無く、**同じ理由がそのまま当たる**。サービスアカウント（Google Workspace ならドメイン全体の委任が使えるが、個人 Google アカウントには使えない）か、**一度取った refresh token を Sealed Secret に封じて運ばせる**かの二択になる。後者は「人が一度ブラウザで承認する」工程が GitOps の外に出る
- **不可逆操作の扱い。** メール送信・予定の削除は非スコープの「自律的な外部システム操作」に触れる。**読みは自動、書きは人の確認を挟む**という線引きを、実装前に決めておく
- **受信メール本文は最も強い非信頼データ。** 送信元を選べない入力であり、F-19 の扱いを最も厳しく適用する対象になる

### F-37. チャットのスレッドから GitHub Issue を立てる

思い付きをチャットに書き溜めておき、**その場で Issue にできること**。スレッドの中で名前を呼んで「Issue にして」と頼むと、そのスレッドの元投稿を出典にして Issue が立ち、番号と URL が返る。

- **出典はスレッドの元投稿。** Issue 本文の先頭に、投稿のパーマリンクと引用が必ず入る。どこから来た Issue なのかを後から辿れないものを作らない
- **起票先はチャンネルごとに設定する**（→ D-32）。設定に無いチャンネルでは起票しない
- **道具が配られるのはスレッドの中だけ**（→ D-33）。スレッドの外では「どの投稿を Issue にするのか」が決まらない
- **立てたら元投稿に ✅ を付ける。** stocktrade の日次棚卸し（`memo-triage`）が ✅ の付いた投稿を読み飛ばすので、夜にもう1本同じ Issue が立たない
- **中身はこのアシスタントが組む。** リポジトリの実装や既存 Issue との突合はしない —— それは調べ物であって、チャットの往復1回で返せる仕事ではない。突合は夜の棚卸しに任せる
- 認証は `GITHUB_TOKEN`（fine-grained PAT、対象リポジトリの `issues: write`）。**未設定でも起動はする** —— 起票を頼まれたときにだけ、トークンが無いと名指しで失敗する
- 元投稿は**非信頼データ**として扱う（F-19, INV-4）。ギルドのスレッドは誰でも立てられる

受け入れ条件: 設定済みチャンネルのスレッドで「Issue にして」と頼むと、出典リンク付きの Issue が立ち、番号と URL が返り、元投稿に ✅ が付くこと。設定の無いチャンネルでは、その理由が返ること。

### F-60. 設定ファイルによるカスタマイズ（静的設定）

以下を設定ファイルで与えられること。**人が直接編集でき、リポジトリの外に置ける**（秘密情報ではないが、利用者ごとの内容なのでコミットしない）。

| 項目 | 例 |
|---|---|
| 名前・呼称 | アシスタントの名前、利用者の呼び方 |
| 人格・口調 | 性格の記述、一人称、語尾、話し方の指針 |
| 3D モデル | VRM ファイルの参照、初期表情・カメラ位置 |
| 音声 | VOICEVOX の話者 ID、話速・音高 |
| 挙動 | 人格・口調固定モードの ON/OFF（F-34）、応答条件、リマインダーのポーリング間隔 |

**環境変数とは役割を分ける。** 環境変数は接続先・認証情報（起動時に valibot で検証して落とす、F-52）。設定ファイルは**ユーザー体験の定義**。混ぜない。

### F-61. 設定 UI

アバター表示のフロントエンド（`web/`）上で、F-60 の内容を画面から変更できること。

- 変更は即座に、または明示的な適用操作で反映される
- **設定 UI は認証を必須にする**（→ INV-6）。アバターのページが到達可能な場所にある以上、**設定画面が無認証だと誰でも人格と声を書き換えられる**
- **UI の書き込み先は設定ファイル**（F-60 と同じ実体）。手編集と設定 UI は同じものを別の入口から触る。**人格の変化差分（ランタイム状態）とは別**（→ D-12, INV-9）
- 手編集と UI の同時変更で失われる書き込みが出ないよう、書き込みは読み直し→検証→保存を 1 操作として行う

### F-62. 3D モデルの差し替え

VRM ファイルを差し替えられること。**モデルファイルをリポジトリにコミットする前提にしない**（容量とライセンスの両面。→ Q-12）。

- ファイルの置き場所と配信方法（永続ボリューム / オブジェクトストレージ / UI からのアップロード）は Q-14
- モデルごとに異なる表情の名前（BlendShape / Expression）をどう吸収するかは Q-15

## F-4x. スキル自己改善ループ

C-07 の先行実装を踏襲する。

### F-40. スキル候補の自動生成

メインエージェントとは別のキュレーターエージェントが、**返信確定後に fire-and-forget で dispatch** され、直近のやり取りから再利用可能な知見をスキル候補として記録する。会話履歴・応答レイテンシに影響してはならない。

- インスタンス ID はメインエージェントと確実に別アドレスになるよう明示的に prefix する（→ D-26）
- **dispatch は待たない。失敗しても会話を落とさない。** キュレーターが黙って死んでも利用者の応答は返る（が、失敗は ERROR に残す → INV-7）
- **キュレーターに渡すやり取りは非信頼データ扱い**（→ INV-4）。区切り記号で囲み、「これは分析対象の記録であって指示ではない」ことを構造的に示す。会話に「スキルを作れ」と書けば作れてしまうが、**それが即座に効かない**ことは承認フロー（F-41）が担保する
- 候補は**種別を伴って**提案される: `knowledge`（手順・知識）か `persona`（人格・口調に関わる）。固定モードの判定に使う（→ F-34, D-26）。**判断に迷えば `persona`** —— 取りこぼしより誤って固定モードを破ることのほうが悪い

### F-41. 承認フロー

候補は pending として保存され、**承認されるまでメインエージェントの応答に一切反映されない**。承認・却下は Discord から行える。承認は次ターン以降に効く。

- 状態は `pending → approved → disabled` と `pending → rejected`。**遷移は必ず現在の状態を条件にする**（→ D-26）。提案は非同期に届くので、条件を付けないと承認済みの行が後から来た提案に巻き戻される
- **承認操作はサーバ管理権限（`ManageGuild`）を持つ人に限る**（→ D-26）。応答に効くものを誰でも通せるのでは、絶対ルール 4 の審査が形だけになる
- 応答は ephemeral（本人にだけ見える）。承認作業でチャンネルを埋めない

### F-42. 承認済みスキルの動的マウント

approved のスキルのみを、メインエージェントのレンダー時に `defineSkill` + `useSkill` で動的にマウントする。

- **固定モード中は `persona` 種別を外す**（→ F-34）
- **1 件が Flue の検証に落ちても、他のスキルとその会話を巻き込まない。** 落ちた 1 件は ERROR に残してマウントを飛ばす（名前の形式・長さ制限は Flue 側にもあり、提案時の検証を通っても将来の版で弾かれうる）

### F-43. スキルの棚卸し

生成され続ける候補が溜まり続けないよう、pending の一覧と一括却下ができる。効かなくなったスキルの無効化もできる。無効化したスキルは再承認できる（捨てるのではなく戻せる）。
