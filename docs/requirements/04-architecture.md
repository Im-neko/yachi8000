# 04. アーキテクチャ方針

共通の層構成・依存方向・エラーハンドリングは `dev:development-principles` に従う。**ここには本プロジェクト固有の差分と不変条件だけを書く。**

---

## 不変条件

後続フェーズの設計は、ここから継承する不変条件を明示的に再掲すること。散文の中に埋めると数フェーズで風化する。

**INV-1. 非公式手段を使わない。** Discord への映像送信は、動く実装が世に存在しても採用しない（→ C-01）。

**INV-2. 3D 描画はブラウザに閉じる。** サーバは状態とイベントを配信するのみ。サーバサイドの WebGL / ヘッドレスレンダリングは実装しない（→ C-06）。

**INV-3. LLM に副作用を持たせない。** LLM は分類・要約・書き換え・判断のみを行い、構造化された結果を返す。外部システムの操作は、その結果を受け取った決定的なコードが行う。

**INV-4. 外部由来のテキストを指示として扱わない。** 通知本文・Web 検索結果・取得したドキュメントは非信頼データ。LLM へ渡す際に、データと指示が構造的に区別できる形にする（→ F-19）。

**INV-5. 発話は単一の再生経路を通る。** 会話応答・通知の読み上げ・リマインダーは、すべて同じ優先度付き再生キューに入る。経路を増やすと順序が非決定になる（→ F-17）。**文単位の分割合成（D-11）もこのキューの内側に閉じ込め、呼び出し側に意識させない。**

**INV-6. アシスタントに発話させられる入口は必ず認証する。** 到達性（localhost バインド等）を認証の代わりにしない（→ F-18）。

**INV-7. 縮退は必ずログに出す。** フォールバック禁止の例外として認めるのは「意図的な部分縮退」のみで、それは WARN 以上で記録されていなければならない。

**INV-8. 静的設定とランタイム状態を同じ場所に置かない。** 人が決める設定（名前・既定の人格・VRM 参照・話者 ID・固定モード）と、プロセスが積み上げる状態（人格の変化差分・学習したスキル）は別の実体に持つ（→ D-12）。

**INV-9. 設定ファイルへの書き込みは、人の操作を契機とするものだけ。** 設定 UI のハンドラは書いてよい（利用者がボタンを押した結果だから）。**会話ロジック — エージェント・スキル・ツール・poller・停止処理・定期処理 — は書かない。** 禁じたいのは「プロセスが勝手に人の設定を書き換える」ことであって、「プロセスを経由して人が設定を変える」ことではない。
**INV-10. 音声入力は経路によらず単一のユースケースに集まる。** Discord VC も Web のマイクも infrastructure の 1 実装に過ぎず、application は**どこから来た音声かを知らない**（→ D-19, F-13）。話者 ID は infrastructure の入口で正規化し、Discord の SSRC も Web のセッション ID も上の層へ漏らさない。

**INV-11. 記憶・人格・スキルはひとつ。分けるのは会話の文脈と話者だけ。** 場（サーバ・DM・将来の Web セッション）で分けるのは Flue が持つ短中期の会話履歴のみで、長期記憶・人格・スキル・リマインダーは全体でひとつの入れ物に持つ（→ D-35, F-04）。**「誰の話か」は分離ではなく属性**として持つ（`speakerId`、→ F-05）。

## 層の責務

| 層 | このプロジェクトでの中身 | 依存してよい先 |
|---|---|---|
| domain | 会話ターン、人格（既定 + 変化差分の合成規則）、リマインダー、スキル候補、発話イベント、通知。および各 port の interface | なし |
| application | 「発話を受けて応答を作る」「通知を読み上げ文に変える」「リマインダーを発火させる」「スキル候補を評価する」「人格を組み立てる（固定モードの判定を含む）」 | domain のみ |
| infrastructure | Discord Bot / VC、VOICEVOX クライアント、STT、LLM プロバイダ、SQLite リポジトリ、pgvector リポジトリ | 何でも |
| interfaces | HTTP ルート（通知 API・ヘルスチェック）、アバター用 WebSocket、表示整形（Discord embed・CLI 出力等） | domain / application |
| 合成ルート | `app.ts`、`agents/*.agent.ts` | 全層 |

**Flue の `agents/` `tools/` は層ではなくフレームワーク接触面。** ユースケースの実体は `application/` に置き、`tools/` はそれを呼ぶだけの薄い層にする。ここを混ぜると、Flue を差し替えられなくなるだけでなく、ユースケースが単体テストできなくなる。

依存方向は **CI で機械的に検査する。** application → infrastructure の通常依存を検出したら落とす。目視レビューでは守られない（house rule に実例あり）。

## 共有される書き込み先の棚卸し

house rule に従い、フェーズ分割の前に「資源 × 書き手 × プロセス」を一度洗い出す。フェーズは「何を移すか」で割られるが、詰まる事実は資源ごとに決まる。

| 資源 | 書き手 | プロセス | 注意点 |
|---|---|---|---|
| Discord Gateway 接続 | Bot クライアント | agent 1 プロセスのみ | **k8s のレプリカは 1、更新戦略は Recreate。** ここを見落とすと RollingUpdate で新旧同時起動する。単一トークンで複数 Gateway 接続を張ったときの挙動は**類推**（→ Q-13 で要確認）だが、VC 接続と再生キューが 1 プロセスに閉じている以上、レプリカ 1 は結論として動かない |
| Discord VC の音声再生 | 会話応答 / 通知 API / リマインダー | 同上 | 3 経路が同じキューに入る（→ INV-5, F-17） |
| 音声入力 | Discord VC 受信（A）/ Web のマイク（B） | agent | **2 経路が同じユースケースに集まる**（→ INV-10, D-19）。話者 ID は infrastructure の入口で正規化する |
| 会話履歴 SQLite（`FLUE_DB_PATH`） | Flue ランタイム | agent | 自動圧縮も書き手。**独自に触らない。ここに自分のテーブルを混ぜない**（→ D-24） |
| リマインダー（ランタイム状態 SQLite、`APP_DB_PATH`） | ツール（登録・削除）/ poller（発火更新） | agent（poller は同一プロセス内の定期処理） | poller とツールが同じ行を触る。**発火の印は届ける前に立てる**（at-most-once、→ D-23） |
| スキル（同上） | キュレーターエージェント（提案）/ 承認コマンド | agent（**別インスタンス ID**） | 提案は fire-and-forget で非同期。**状態遷移は必ず現在の状態を条件にする**（→ D-26） |
| ベクタストア（Postgres + pgvector） | 長期記憶の記録 | agent（**専用インスタンス**。共用 PG には相乗りしない） | **ひとつの空間に持つ。分離のための列は置かない**（→ D-35）。代わりに `speaker_id` で「誰の話か」を持つ（→ F-05） |
| 設定ファイル（静的設定） | 手編集、および**設定 UI のハンドラ**（＝人の操作） | agent（読み取り）+ 設定 UI（書き込み） | **会話ロジックからは書かない**（INV-9）。手編集と UI が同じ実体を触るので、書き込みは読み直し→検証→保存を 1 操作で行う |
| 人格の変化差分（ランタイム状態） | エージェント | agent | 設定ファイルとは別の実体。固定モード時は**書き続けるが読まない** |
| VRM ファイル | 人（アップロード / 配置） | agent は配信するだけ | 置き場所は Q-14。リポジトリにはコミットしない |
| 音声合成エンジン | 合成リクエスト | **独立した Deployment**（agent とライフサイクルを共有しない） | CPU 合成でも RTF 0.14〜0.31 で、同時 2 リクエストでも破綻しないことを実測済み（C-14）。**効くのは合計時間ではなく初音レイテンシ**なので文単位で分割合成する（C-15, D-11）。**agent が依存してよいのは接続情報だけ**（D-05） |
| LLM プロキシ | 応答生成 / 通知の書き換え / スキル提案 | 別プロセス（→ Q-01） | レート制限・同時接続。スキル提案が会話のレートを食わないこと |
| Web 検索 API（Brave） | 検索ツール（読み取りのみ） | 外部サービス | **無料枠は月間クォータ制。** 会話ごとに引けば尽きる。件数上限を置き、結果は非信頼データとして扱う（→ INV-4, D-27） |
| 音声バッファ・合成キャッシュ | STT / TTS | agent | 永続ボリュームに置かない。`emptyDir` + `sizeLimit`（→ C-12） |

## 永続化するもの一覧

**「何が、どこに、誰の書き込みで貯まるか」の一覧。** 散らばると必ず二重管理になるので、ここを正典にする。

| # | 何を | どこに | 書き手 | 消えると何が失われるか |
|---|---|---|---|---|
| 1 | **会話履歴（短中期）** | **Flue 組み込みの SQLite**（`FLUE_DB_PATH`） | Flue ランタイム（自動圧縮も） | 直近の話の流れ。**独自の履歴管理を実装しない**（F-02） |
| 2 | **長期記憶（知識・人物・好み）** | **専用 Postgres + pgvector** | 明示的な記録ツール | 「前に話したこと」。会話履歴の圧縮で消えても、こちらには残る（F-30、D-20） |
| 3 | **スキル** | **ランタイム状態 SQLite**（`APP_DB_PATH`） | キュレーターエージェント（提案）/ 承認操作 | 学習した手順・知識（F-40〜F-43） |
| 4 | **人格の変化差分と履歴** | 同上 | エージェント | 育った人格。**捨てれば既定の人格に戻る**（F-33、D-12） |
| 5 | **リマインダー** | 同上 | ツール（登録・削除）/ poller（発火更新） | 予定（F-31） |
| 6 | **静的設定** | **設定ファイル** | 人の操作のみ（手編集 / 設定 UI） | 名前・既定の人格・VRM 参照・話者 ID・固定モード（F-60、D-12、INV-9） |
| 7 | **VRM ファイル** | 同上のストレージ | 人（配置 / アップロード） | アバターの見た目（F-62、Q-14） |
| 8 | **話者のプロフィール** | **ランタイム状態 SQLite**（`APP_DB_PATH`） | 初回の自動登録（表示名）/ 会話の中でのツール呼び出し | 「誰と話しているか」。消えると全員が初対面に戻る（F-05、D-35） |
| — | 音声バッファ・合成キャッシュ | `emptyDir`（`sizeLimit` 付き） | STT / TTS | **何も失われない。永続化してはいけない**（C-12） |

**1 と 2 の切り分けが肝心。** 会話履歴は Flue が圧縮して落としていくので、**残したい事実は 2 へ明示的に書き出さないと消える。** これは 先行実装と同じ切り分け。

**4 と 6 は別の実体に置く**（INV-8）。**3 と 6 も別**で、スキルはエージェントが書き、設定ファイルは人が書く。

**2 と 8 も別。** 8 は**話しかけてくる相手**のプロフィール（判別できる人に紐付く鍵つきの実体）で、2 は**話題に出る人を含む事実**（本文の中身）。混ぜると「判別できる相手」と「話に出てくる人」が同じ実体になり、どちらの鍵で引けばよいか決まらなくなる（→ F-05）。

**1 と 3〜5 も別ファイルにする**（→ D-24）。どちらも SQLite だが、1 は**スキーマも圧縮も Flue が所有する** DB で、こちらが同居させてよい保証がない。**同じ PVC の上の、別の 2 ファイル**（`FLUE_DB_PATH` / `APP_DB_PATH`）に置く。

> **⚠ `APP_DB_PATH` を PVC 上に向け忘れると、リマインダー・スキル・人格差分が Pod 再起動ごとに消える。** 既定値はコンテナ内の相対パス（`./data/yachi.db`）なので、**黙って消える**。手順は `docs/setup/deploy.md`。

## 音声合成エンジンの配置

**独立した Deployment として動かし、agent には接続情報だけを渡す**（→ D-05）。利用者が別途 `docker run` しておく前提にはしないが、**agent と同じライフサイクルにも縛らない。**

- **開発時**: `compose.yaml` の独立したサービス。`docker compose up` で一緒に立ち上がる
- **運用時**: `helm-charts/yachi8000/` の**別 Deployment + ClusterIP Service**。サイドカーにしない
- 接続先は `VOICEVOX_URL`、話者は設定項目。**コードにホスト名も既定の話者も埋め込まない**
- イメージは **CPU 版**（→ D-11。実測で GPU 不要）

**なぜ独立させるか**: 運用者がエンジン・話者を差し替えられることが要件だから。イメージの差し替え・別ホストの既存エンジンの参照・話者の変更が、**agent を触らずに values か環境変数だけで完結する。**

**⚠ 差し替え可能にした結果、依存する API の契約が重要になった。** yachi8000 は `/synthesis` に加えて **`/audio_query`（モーラ単位の音素と長さ）をリップシンクに使う**（F-21）。差し替え先は VOICEVOX 互換でなければならず、**起動時に検証して満たさなければ落とす**（合成だけ通ってリップシンクが黙って壊れるのを防ぐ）。

## 通知読み上げの経路

```
外部システム
   │ POST（送信元ID + 本文 + トークン）
   ▼
interfaces/  通知ルート ── 認証（F-18）→ 受理応答を即返す
   │                       └─ 本文は非信頼データとしてマーク（INV-4）
   ▼
application/ 通知ユースケース
   │ ① LLM で自然文へ書き換え（失敗したら決定的テンプレート + WARN ログ）
   │ ② 優先度付き発話キューへ投入（INV-5）
   ▼
infrastructure/ VOICEVOX 合成 → Discord VC 再生
   │
   └─▶ interfaces/ WebSocket → アバターの口・表情（F-21）
```

VC 未接続時の扱い（テキストへ転送 / 破棄）は設定で切り替える。**どちらでも「読み上げられなかった」ことは必ずログに残す**（INV-7）。

### リマインダーの発火経路（通知との違い）

```
poller（固定間隔）
   │ 期限到来を検知 → 発火済みの印を立てる（届ける前。at-most-once）
   ▼
application/ リマインダーユースケース
   │ ① 保存済みの文面を素材に、LLM が伝える一言を組み立てる（→ D-30）
   │    失敗したら定型文へ縮退し、WARN を出す（INV-7）
   │ ② 登録されたチャンネルへテキスト送信（常に）
   │ ③ 同じサーバの VC に接続中なら、リマインダー優先度で発話キューへ（INV-5）
   ▼
infrastructure/ Discord テキスト送信 / VOICEVOX 合成 → VC 再生
```

**通知との違いは 2 点**: テキスト配信が縮退ではなく**常の経路**、そして **VC は「同じサーバ」でなければ読まない**（別サーバの VC にいる人へ内容が漏れる）。**文面づくりは通知と同じ形**（D-30 で D-08 を覆し、経路ごとの違いを 1 つ減らした）。

## 技術的不確実性の順序

不確実性の高いものから PoC で潰す。**設計を先に固めてから PoC すると必ず手戻る。**

1. **Discord VC の発話区間の切り出し**（→ C-09, Q-03）— 受信の可否と話者分離は解決済み（必要なパッケージは導入済み、`ssrcMap` が標準提供）。**残るのは「一文を話し切るまで切れずに取れるか」**。駄目でも B（Web のマイク入力）は元から作る予定なので（D-19）、**手戻りではなく前倒しになる**
2. ~~**STT の選定と実行環境**~~ — **解決済み。さくらの AI Engine の Whisper を LLM プロキシ経由で使う。GPU 不要**（→ D-16）
3. ~~**LLM プロキシの k8s 化**~~ — **解決済み。API キー方式のモデルのみを使うため bind mount が不要になった**（→ D-10）
4. **リップシンク用データの取得経路**（→ Q-07）— VOICEVOX の `audio_query` で足りるか
5. ~~**Flue の Discord 連携の有無**~~ — **解決済み。Flue に Discord アダプタは無く、全て自前実装になる**（→ C-10, D-09）
