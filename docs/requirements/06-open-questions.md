### Q-03. Discord VC の音声受信で、発話区間をまともに切り出せるか

**期限: 音声入力フェーズ（順 7）の A 着手前**

**「受信できるか」はほぼ解決した**（→ D-19）。必要なパッケージは全て導入済みで、話者分離も `ssrcMap` で標準提供される。**残る実質的な不確実性は発話区間の切り出し。**

`EndBehaviorType.AfterSilence` は**ユーザーがまだ話している最中にストリームを終わらせてしまう**不具合が報告されている（[discord.js#8105](https://github.com/discordjs/discord.js/issues/8105)）。文の途中で切れると、そのまま STT に渡しても意味の通らない断片になる。

**PoC の合格条件**:
- VC に参加した Bot が、特定ユーザーの音声を Opus ストリームとして受信できる
- **一文を話し切るまで切れずに区間を取れる**（ここが本命）
- 複数人が同時に話したときに話者を分離できる
- PCM へデコードして STT に渡せる形にできる

**切り出しが不安定だった場合の手当**（優先順）:
1. `EndBehaviorType.Manual` にして**自前で無音閾値を持つ**（PCM を貯めて自分で区切る）
2. プッシュ・トゥ・トーク相当にして、**区間の判定を機械に任せず操作で明示する**
3. B（Web のマイク入力）を前倒しする

**リスクの位置づけが下がった**: B は元から作る予定なので（D-19）、A が駄目でも計画の前倒しであって手戻りではない。**以前「本プロジェクト最大の技術的不確実性」と書いていたが、その位置づけは取り下げる。**

`@discordjs/voice` に receiver API があることは既知だが、本環境での動作は未検証（C-09）。既存 `discord-vc` プラグインは送信のみ。

**確かめること**（最小 PoC の合格条件）:
- VC に参加した Bot が、特定ユーザーの音声を Opus ストリームとして受信できる
- 発話区間（無音区間による切り出し）を検出できる
- 複数人が同時に話したときに話者を分離できる
- PCM へデコードして STT に渡せる形にできる

**この PoC が通らない場合**、音声入力の経路を Discord 以外（自前 Web ページのマイク入力）に変える必要があり、D-02 の見直しになる。

### Q-07. リップシンクのデータをどこから取るか

**期限: アバターフェーズ（順 6）の設計前**

VOICEVOX の `/audio_query` はモーラごとの音素と長さを含むアクセント句を返す。これをそのままリップシンクに使えるか、音量エンベロープを別途計算する必要があるかが未確認。

**構造は確認済み**（2026-09-11、VOICEVOX 0.25.1 実測）。モーラは
`{text, consonant, consonant_length, vowel, vowel_length, pitch}` を持ち、アクセント句には `pause_mora` も付く。
**音素と長さは揃っているので、口形の切り替えタイミングは計算できる。** フェーズ 3 の起動時契約検証（F-12）でも
`accent_phrases[].moras[].vowel_length` の存在を確かめており、満たさないエンジンでは起動しない。

**残る確認事項**: `speedScale` を掛けたときに長さがどう伸縮するか（`vowel_length` に反映されるのか、再生側で按分するのか）と、
口形を VRM の Expression にどうマッピングするか（→ Q-15）。前者はアバターフェーズで実測する。

### ~~Q-08. 人格設定の実体と、会話による更新の可否~~ → D-12 / D-13 で決定（2026-09-11）

### ~~Q-10. フェーズの優先順~~ → 確定（2026-09-11 に更新、オーナー判断）

### Q-16. 固定モードのとき、人格に関わるスキル候補をどう扱うか

**期限: スキル自己改善フェーズ（順 4）の実装前**

F-34 は「固定モードでも人格・口調に関わらないスキルは通常どおり提案・承認できる」としているが、F-33 は人格の変化が**会話とスキル自己改善ループの両方**から来るとしている。**つまり一部のスキル候補は、それ自体が人格の変化である。**

決めること:

- **誰が「人格に関わる候補」と判定するのか。** キュレーターエージェントに分類させるのか、スキルの種別を候補生成時に構造化して持たせるのか
- 固定モード中、人格に関わる候補をどう扱うか。生成して pending のまま置く / 生成するが承認できない / マウントはするが適用しない
- 分類が外れた場合の扱い。**house rule の「確信度の低い自動判断を、確信ありげに適用しない」に照らすと、判定に迷う候補は「人格に関わる」側へ倒すのが安全側**

**先に確かめること**: そもそも「手順・知識のスキル」と「人格・口調のスキル」が実運用で分離できるのか。分離できないなら、固定モード中はスキルの適用自体を止めるほうが素直かもしれない。

### Q-19. VOICEVOX の同梱をやめ、さくらの音声合成に寄せるか

**期限: 急がない（D-05 の同梱で動くため）**

さくらの AI Engine は **VOICEVOX 互換の `/v1/audio/speech`** を持つ。これを使えば VOICEVOX Pod の同梱（D-05）をやめられ、デプロイが 1 つ減る。

**ただし現時点で寄せる理由は薄い**:
- ローカル VOICEVOX は実測 RTF 0.14〜0.31 で十分速い（C-14）。ネットワーク越しにすると**初音レイテンシは確実に悪化する**
- 話者の選択肢・話速や音高の調整が同等に効くかは未確認

**確かめること**: さくら側で使える話者と、`/audio_query` 相当（モーラ単位の音素と長さ）が取れるか。**取れないならリップシンク（F-21, Q-07）が成立しなくなる**ため、その時点で選択肢から外れる。

### Q-20. 開発用とクラスタ用のモデル定義がずれるのをどう防ぐか

**期限: モデルを次に追加するとき**

同じ `model_list` が 2 箇所にある。

- 開発用の LLM プロキシの `config/config.yaml`（開発時）
- インフラ定義リポジトリの `helm-charts/litellm/templates/configmap.yaml`（運用時・正典）

選択肢: 片方を生成元にして機械的に同期する / 開発時もクラスタの litellm を向く（ネットワーク前提が増える）/ CI で差分を検出して落とす。

**先に確かめること**: 開発時に本当にローカルの LiteLLM が要るのか。`llm.<自宅ドメイン>` を向ければ 1 箇所で済む。

### Q-21. クラスタ上の別アプリが master key を持っている状態をどうするか

**期限: 急がない（動作はしている）**

D-17 の集約で、クラスタ上の別アプリの `OPENAI_API_KEY` に **litellm の master key そのもの**を入れた。master key は管理者権限に相当するため、**1 つの利用者に管理者キーを配っている**状態になっている。

現状これで動く（クラスタ上で疎通確認済み）が、利用者が増えるほど不適切になる。

選択肢:
- 仮想キー（Postgres 併用）に移行し、利用者ごとにスコープされたキーを発行する。使用量の内訳も見えるようになる
- 現状維持（利用者が自分だけである限り実害は小さい）

**D-20 で yachi8000 用に現行版の Postgres を立てることが決まったため、移行のコストが下がった。** ただし LiteLLM と yachi8000 が同じ DB を共有するかは別途判断が要る（共有資源の参加者が増える）。

**yachi8000 も同じ問題を抱える。** yachi8000 に master key を渡すのか専用キーを発行するのかは、**外部公開した `llm.<自宅ドメイン>` を自分以外が使い始める前に**決めること。

### Q-22. 誤った API キーが 401 ではなく 400 を返す

**期限: 急がない（アクセスは正しく拒否されている）**

**確認済みの挙動**（2026-09-11、クラスタ上で実測）:
- キー無し → `401 Authentication Error, No api key passed in.`（正しい）
- **誤ったキー → `400 {"message":"No connected db.","type":"no_db_connection"}`**

**原因**: master key 単体構成では仮想キーの照会先 DB が無いため、master key 以外のキーは DB 照会の段階で落ちる。**アクセスは拒否されているのでセキュリティ上の問題ではない**が、ステータスコードが不正確でクライアントが認証失敗として扱えない。

Q-21 で仮想キーに移れば自然に解消する。
