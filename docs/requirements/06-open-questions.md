### Q-03. Discord VC の音声受信で、発話区間をまともに切り出せるか

**期限: 音声入力フェーズ（順 7）の A 着手前**

**「受信できるか」はほぼ解決した**（→ D-19）。必要なパッケージは全て導入済みで、話者分離も `ssrcMap` で標準提供される。**残る実質的な不確実性は発話区間の切り出し。**

`EndBehaviorType.AfterSilence` は**ユーザーがまだ話している最中にストリームを終わらせてしまう**不具合が報告されている（[discord.js#8105](https://github.com/discordjs/discord.js/issues/8105)）。文の途中で切れると、そのまま STT に渡しても意味の通らない断片になる。

**PoC の合格条件**:
- VC に参加した Bot が、特定ユーザーの音声を Opus ストリームとして受信できる
- **一文を話し切るまで切れずに区間を取れる**（ここが本命）
- 複数人が同時に話したときに話者を分離できる
- PCM へデコードして STT に渡せる形にできる

**切り出しが不安定だった場合の手当**（優先順）:
1. `EndBehaviorType.Manual` にして**自前で無音閾値を持つ**（PCM を貯めて自分で区切る）
2. プッシュ・トゥ・トーク相当にして、**区間の判定を機械に任せず操作で明示する**
3. B（Web のマイク入力）を前倒しする

**リスクの位置づけが下がった**: B は元から作る予定なので（D-19）、A が駄目でも計画の前倒しであって手戻りではない。**以前「本プロジェクト最大の技術的不確実性」と書いていたが、その位置づけは取り下げる。**

`@discordjs/voice` に receiver API があることは既知だが、本環境での動作は未検証（C-09）。既存 `discord-vc` プラグインは送信のみ。

**確かめること**（最小 PoC の合格条件）:
- VC に参加した Bot が、特定ユーザーの音声を Opus ストリームとして受信できる
- 発話区間（無音区間による切り出し）を検出できる
- 複数人が同時に話したときに話者を分離できる
- PCM へデコードして STT に渡せる形にできる

**この PoC が通らない場合**、音声入力の経路を Discord 以外（自前 Web ページのマイク入力）に変える必要があり、D-02 の見直しになる。

### ~~Q-07. リップシンクのデータをどこから取るか~~ → D-38 で決定（2026-09-20）

**`/audio_query` のモーラだけで足りる。音量エンベロープは要らない。** 残っていた `speedScale` の扱いも実測で決着した ——
**`/audio_query` が返す長さは常に等倍で、伸縮は `/synthesis` の側で全体を一律に `1/speedScale` する**（ずれ 1% 未満）。
口形の時刻は「モーラの長さ ÷ `speedScale`」で計算する。母音から VRM プリセットへの対応表も D-38 にある（→ Q-15 も決着済み）。

以下は経緯の記録。

**期限: ~~アバターフェーズ（順 6）の設計前~~（決着済み）**

VOICEVOX の `/audio_query` はモーラごとの音素と長さを含むアクセント句を返す。これをそのままリップシンクに使えるか、音量エンベロープを別途計算する必要があるかが未確認。

**構造は確認済み**（2026-09-11、VOICEVOX 0.25.1 実測）。モーラは
`{text, consonant, consonant_length, vowel, vowel_length, pitch}` を持ち、アクセント句には `pause_mora` も付く。
**音素と長さは揃っているので、口形の切り替えタイミングは計算できる。** フェーズ 3 の起動時契約検証（F-12）でも
`accent_phrases[].moras[].vowel_length` の存在を確かめており、満たさないエンジンでは起動しない。

**残っていた確認事項**: `speedScale` を掛けたときに長さがどう伸縮するか（`vowel_length` に反映されるのか、再生側で按分するのか）と、
口形を VRM の Expression にどうマッピングするか（→ Q-15）。**どちらも決着した**（前者は D-38 で実測、後者は D-36 の 1）。

### Q-21. クラスタ上の別アプリが master key を持っている状態をどうするか

**期限: 急がない（動作はしている）**

D-17 の集約で、クラスタ上の別アプリの `OPENAI_API_KEY` に **litellm の master key そのもの**を入れた。master key は管理者権限に相当するため、**1 つの利用者に管理者キーを配っている**状態になっている。

現状これで動く（クラスタ上で疎通確認済み）が、利用者が増えるほど不適切になる。

選択肢:
- 仮想キー（Postgres 併用）に移行し、利用者ごとにスコープされたキーを発行する。使用量の内訳も見えるようになる
- 現状維持（利用者が自分だけである限り実害は小さい）

**D-20 で yachi8000 用に現行版の Postgres を立てることが決まったため、移行のコストが下がった。** ただし LiteLLM と yachi8000 が同じ DB を共有するかは別途判断が要る（共有資源の参加者が増える）。

**yachi8000 も同じ問題を抱える。** yachi8000 に master key を渡すのか専用キーを発行するのかは、**外部公開した `llm.<自宅ドメイン>` を自分以外が使い始める前に**決めること。

**2026-09-11 時点の結論: yachi8000 も master key を持たせた。** 公式ドキュメント（`docs/proxy/virtual_keys`）で確認したとおり、LiteLLM の仮想キーは `DATABASE_URL`（Postgres）を前提としており、**設定ファイルや環境変数で静的にキーを列挙する方法・DB 無しで仮想キーを使う方法は存在しない**。現行の LiteLLM には `DATABASE_URL` が無いため、渡せるキーは master key しかない。

専用キーに移るには LiteLLM 側に Postgres を足す必要があり、**共有サービスに新しい起動時依存を増やす**（DB が落ちると全利用者が LLM を使えなくなる）。yachi8000 側は SealedSecret の再 seal と Pod 再起動だけで切り替わるので、後追いで移行してもコストは増えない。

### Q-22. 誤った API キーが 401 ではなく 400 を返す

**期限: 急がない（アクセスは正しく拒否されている）**

**確認済みの挙動**（2026-09-11、クラスタ上で実測）:
- キー無し → `401 Authentication Error, No api key passed in.`（正しい）
- **誤ったキー → `400 {"message":"No connected db.","type":"no_db_connection"}`**

**原因**: master key 単体構成では仮想キーの照会先 DB が無いため、master key 以外のキーは DB 照会の段階で落ちる。**アクセスは拒否されているのでセキュリティ上の問題ではない**が、ステータスコードが不正確でクライアントが認証失敗として扱えない。

Q-21 で仮想キーに移れば自然に解消する。

### Q-23. Google カレンダー / Gmail の認証を k8s 上でどう成立させるか

**期限: F-36 をフェーズに置く前**

D-10 は「**OAuth 経由のモデルは k8s に載らない**」として API キー方式を選んだ。**Google API にはその逃げ道が無い** —— API キーで読めるのは公開データだけで、個人のカレンダーとメールには OAuth か サービスアカウントが要る。D-10 と同じ壁に、今度は回避策なしで当たる。

選択肢:

| | 仕組み | 問題 |
|---|---|---|
| (a) サービスアカウント + ドメイン全体の委任 | 人の承認なしにアクセスできる | **Google Workspace が要る。個人の Google アカウントでは使えない** |
| (b) 一度取った refresh token を Sealed Secret に封じる | 個人アカウントでも動く | **「人が一度ブラウザで承認する」工程が GitOps の外に出る。** 失効したら手作業でやり直し |
| (c) 連携しない | — | F-36 を落とす |

**先に確かめること**: 対象が Workspace アカウントか個人アカウントか。ここで (a) が使えるかどうかが決まり、決まれば残りはほぼ機械的に follow する。

**同時に決めること**（認証とは独立に、実装前に線を引く）:

- **不可逆操作の扱い。** メール送信・予定の削除は、非スコープの「自律的な外部システム操作」に触れる。**読みは自動・書きは人の確認を挟む**を既定にするか、書き自体を落とすか
- **受信メール本文は、このシステムが受け取る中で最も強い非信頼データ**（送信元を選べない）。INV-4 / F-19 の適用を最も厳しくする対象になる。「メールを読んで要約して」がそのまま間接プロンプトインジェクションの入口になる

### Q-27. モーション（体の動き）をどう持たせるか → **D-42 で決着**

表情（F-24）は VRM のプリセットに閉じているので、モデルを差し替えても同じ名前で通る。**モーションにはその足場が無い。**

**待機の姿勢は素材なしで済ませた**（2026-09-21、→ F-20）。ボーンを直接寝かせ、呼吸・体重の移し替え・まばたきを手続き的に足してある。**残っているのは「意味のある動き」** —— 頷く・手を振る・考え込む、のように発話の中身に応じて変わるもの。

決まっていないこと:

- **素材をどこから持ってくるか。** VRM にモーションは入っていない。VRMA（VRM Animation）を別ファイルで置くのか、手続き的に作るのか
- **どこに置くか。** VRM と同じ PVC（→ D-36 の 2）に足すのか、イメージに焼くのか。**種類が増えるので「1 ファイル」では済まない**
- **切り替えの繋ぎ。** 表情は重みを寄せるだけで繋がるが、モーションは姿勢が飛ぶ。ブレンドの尺をどこで決めるか
- **判断の粒度。** 発話ごとで足りるのか（表情と同じ呼び出しに質問を足せる）、もっと粗くてよいのか

**表情と同じ経路には載る**（判断は Jev の同じリクエストに質問を 1 つ足すだけで済む）。詰まるのは判断ではなく**見せ方**の側 —— 待機の姿勢と違い、**手続き的に書くと動きの数だけコードが増える。**

**決着**（2026-09-21、→ D-42）: **VRMA で持つ。** 上の 4 つはこう片付いた。

- **素材**: 運用者が置く（pixiv が 7 種を無償配布。クレジット表記が条件で、取り出せる形での二次配布は禁止）
- **置き場所**: VRM と同じ PVC。**種類は固定の語彙**で、設定が持つのは「どのファイルを当てるか」だけ
- **繋ぎ**: 最後の姿勢を保持したまま重みを落として待機へ戻す。待機の姿勢を当ててから身振りを当てるので、触っていないボーンでは呼吸が続く
- **粒度**: 発話ごと。表情と同じ 1 回の呼び出しに相乗りさせる

**残っている問い**: **素材をどう増やすか。** 無償配布の 7 種は挨拶・V サインのような「見せる」動きが中心で、頷く・肩をすくめるといった**会話の相槌に当たるものが揃わない**。自作するか、別の入手先を探すか、語彙のほうを手持ちに寄せるか。


### Q-28. 2 秒に満たない発話をどう扱うか

さくらの AI Engine の Whisper は、**発話が 2 秒に満たないと空文字を返す**（実測 → D-16 の追記の 3）。エラーではなく `{"text": ""}`。パラメータでは外せず、プロキシに他の文字起こしモデルは無い。

**実際に言う言葉に刺さる。** 「ありがとう」1.06 秒、「わかりました」1.13 秒、「今日の天気を教えて」1.87 秒 —— 全部空。常時聞き取り（→ D-47 の 4）だと、**短い相槌が黙って消える。**

候補:

- **(a) そのまま進める。** 空で返ったら WARN と画面表示（「短すぎて聞き取れませんでした」）。**正直だが、「ありがとう」が通らない**
- **(b) 短い発話は引き伸ばしてから送る。** 0.5〜0.7 倍速にすれば 2 秒を超える。**実測で通った**（「わかりました」2.26 秒 → 正しく文字起こし）。決定的なコードで済むが、**エンジンの制限への当て込み**であり、精度への影響は測っていない
- **(c) 文字起こしの口をもう 1 つ持つ。** LiteLLM にもう 1 つ音声認識モデルを足せば下限ごと消える。費用と設定が増える

**決着**（2026-09-22、オーナー判断）: **(b) 引き伸ばして送る。**

**残っているのは「どう引き伸ばすか」だけ。** 2 通りあり、ブラウザ側の実装量がまるで違う:

| やり方 | ブラウザでの実装 | 実測 |
|---|---|---|
| 音程を保って引き伸ばす（time-stretch） | 重なり合わせを自前で書く（約 40 行）か、依存を足す | **通った**（`atempo=0.5` で「わかりました」「今日の天気を教えて」） |
| 素直に再生速度を落とす（音程も下がる） | `OfflineAudioContext` の `playbackRate` だけ。数行 | **未測定** |

**測ろうとした日に無料枠を使い切った**（→ 下の Q-29。落ちていたのではなく 429 だった）。**枠が戻るまで比べられない。** 先に通ることが分かっている「音程を保つ」側で作り、素直な側は測れるようになってから比べる。

**「短い」の判定はブラウザ側で行う。** サーバは受け取った音声をそのまま Whisper へ渡すだけにする —— サーバで直すには webm / mp4 を復号する必要があり、ブラウザには最初から復号済みの音がある。


### Q-29. さくらの Whisper が応答しないときの振る舞い

**落ちてはいなかった（2026-09-23 に判明）。** 2026-09-22 に「25 秒待っても返らない」と書いたのは**誤診**で、実際は**無料枠を使い切って 429 を返していた**。順に測って分かったこと:

| 叩いた先 | 結果 |
|---|---|
| さくらの `/models` | **200 / 0.93 秒**。`whisper-large-v3-turbo` は一覧に居る |
| さくらの `/chat/completions` | **200 / 0.66 秒**。鍵もアカウントも正常 |
| さくらの `/audio/transcriptions`（**直接**） | **429 / 0.3 秒**。`{"error":{"message":"rate limit exceeded"}}`、`retry-after: 60` |
| 同上を 70 秒空けて 4 回 | **4 回とも 429**（分単位の窓では回復しない） |
| LiteLLM 経由で待ち切る | **429 / 181.5 秒** |

**原因は 2 つが重なったもの。**

1. **フリープランの音声認識は 1 ヶ月あたり 50 リクエスト**（[公式](https://ai.sakura.ad.jp/sakura-ai/ai-engine/)。chat は 3,000、embeddings は 10,000 で、**音声認識だけ桁が違う**）。超えるとレート制御がかかり、**翌月まで戻らない**。2026-09-22 の測定（2 秒下限の掃引・境界・反復・パラメータの比較）で使い切った
2. **LiteLLM が `retry-after: 60` を律儀に守る。** `num_retries: 2` なので 60 秒 × 2 回眠ってから 429 を返す（実測 181.5 秒）。こちらの時間切れは 10 秒なので、**429 は一度もこちらへ届かず、「無応答」に見えていた**

**教訓: 上流が即座に返した理由が、プロキシの再試行で時間切れに化ける。** 「落ちている」と判断する前に、**プロキシを飛ばして上流を直接叩く**こと。

**50 リクエスト/月は、検証だけで溶ける。** 常用に入れるなら従量課金（**0.5 円 / 60 秒**）へ切り替えるしかない。**オーナーの判断が要る**（→ 下の「決まっていないこと」の 4 つ目）。

決まっていないこと:

- **時間切れを何秒に置くか。** F-14 の目標は 2 秒。**待てば待つほど「反応しないアシスタント」になる**が、短くしすぎると普通に遅いだけの回を落とす
- **落ちている間、利用者に何を見せるか。** 音声入力は「話しかけたのに無言」が最悪の壊れ方で、**気付く手がかりが無い**（→ INV-7）
- 再試行するか。1 発話 1 リクエストなので再試行はしやすいが、**その間も人は待っている**。**プロキシ側の再試行は害になる** —— 429 の `retry-after` を守って 3 分眠るので、会話には絶対に間に合わない。このモデルだけ `num_retries: 0` にするのが筋（設定は GitOps リポジトリ側）
- **枠をどうするか。** 従量課金へ切り替える（0.5 円 / 60 秒）／翌月のリセットを待つ／別の文字起こしを持つ（→ Q-28 の (c) と同じ口）。**オーナーの判断が要る**

**期限: 音声入力を常用に入れる前。**
