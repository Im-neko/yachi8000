### D-01. リポジトリは `yachi8000`、フレームワークは Flue

**決定**: `yachi8000` リポジトリ（remote: `Im-neko/yachi8000`、**public**）で開発する。Flue Framework 2.x / TypeScript。

public であるため、個人を特定する情報・内部ホスト名・ホストの絶対パスを本文に書かない。他リポジトリは相対的な呼称（先行実装リポジトリ 等）で指す。

**理由**: 先行実装が同じ Flue 構成で稼働しており、エージェント定義・ツール登録・永続化・スキル自己改善ループ・CI/デプロイ経路をそのまま流用できる。自由度の高い設計をしたいという要望に対して、Flue はエージェント・ツール・スキル・サブエージェントを素の TypeScript として書ける点が合う。

**捨てたもの**: ゼロから自作するフレームワーク。会話の永続化・圧縮を自前で持つ負担に見合わない。

### D-02. アバターは自前 Web ページでクライアントサイド描画し、音声だけ Discord VC に流す

**決定**: three.js + `@pixiv/three-vrm` でブラウザ描画。音声の入出力は Discord VC。Slack はテキストのみ。

**理由**: Discord Bot は公式 API で映像を送信できず（C-01）、Slack Huddle には API が無い（C-02）。映像を Discord に流す既存実装はすべて selfbot で ToS 違反にあたり、グローバル CLAUDE.md の「迂回・ハック禁止」に抵触する。また本番ホストはヘッドレス Linux で、サーバサイドの 3D 描画は現実的でない（C-06）。

「ビデオ通話の体験」は、**アバターを見るページと、音声を運ぶ Discord VC を分けること**で達成する。

**捨てたもの**:
- selfbot による Discord 映像送信 — ToS 違反
- 完全自前の WebRTC ビデオ通話 — 認証・NAT 越え・シグナリングの実装量が初期スコープに見合わない。将来 Discord を外す選択肢としては残す
- Unity / VRChat — 常時起動の Windows/GPU 機が別途必要になり、自宅 k8s の運用パターンから外れる

### D-03. LLM は LLM プロキシ経由。Flue にはカスタムプロバイダとして登録する

**決定**: LLM プロキシ（LiteLLM、OpenAI 互換）を単一の入口にし、`app.ts` の `setProvider()` でカスタムプロバイダを登録する。

**理由**: プロバイダを 1 箇所で差し替えられる。加えて、先行実装が踏んだ「`@flue/runtime` のモデルカタログ未収録の新モデルへ切り替えられない」制約を、`createProvider({ api: 'openai-completions', baseUrl })` で回避できることを確認済み（C-03）。

**注意**: LLM プロキシの現構成はホストの認証情報ファイルを bind mount しており、そのままでは k8s に載らない（C-05）。**→ D-10 で解決済み。**

### D-04. デプロイは自宅 k8s（インフラ定義リポジトリ + ArgoCD GitOps）

**決定**: インフラ定義リポジトリに `apps/yachi8000.yaml`（ArgoCD Application）と `helm-charts/yachi8000/` を置く。本リポジトリの CI がイメージを push し、`image.tag` 更新 PR を自動作成する。

**理由**: 先行実装が同じ経路で運用されており、パターンをそのまま流用できる。反映経路が git push のみに固定される（C-11）。

**制約**: **レプリカは 1、更新戦略は Recreate。** VC 接続と音声再生キューが単一プロセスに閉じているため、複数レプリカでは再生順序が非決定になる（INV-5 が壊れる）。可用性より一貫性を取る。

なお「同一トークンで複数 Gateway 接続を張れない」という当初の類推は**誤りだった**（2026-09-11 に実測。→ Q-13）。**2 本目の接続は普通に確立し、1 本目も切れない。** ただし**両方の接続が同じイベントを受け取る**ため、複数レプリカでは 1 通のメッセージに 2 回返信することになる。レプリカ 1 の結論は変わらないが、**理由が「繋げない」ではなく「二重に受け取る」である**点は取り違えないこと。

### D-05. 音声合成エンジンは独立した Deployment。yachi8000 には接続情報だけを渡す

**決定**（2026-09-11 にオーナー判断で改訂）: 音声合成エンジンは **agent とは独立した Deployment** として動かし、**yachi8000 には接続情報（URL）だけを渡す。** 話者の選択は環境変数ではなく静的設定（F-60、`voice.speakerId`）に置く。

| 環境 | 形 |
|---|---|
| 開発時 | `compose.yaml` の独立したサービス。`docker compose up` で一緒に立ち上がる |
| 運用時 | `helm-charts/yachi8000/` の**別 Deployment + ClusterIP Service**。サイドカーにしない |
| 接続 | 環境変数 `VOICEVOX_URL` のみ。話者・話速・音高は設定ファイルの `voice` ブロック（F-60）。**コードにホスト名も既定の話者も埋め込まない** |

**理由**: **運用者が任意のモデル（音声エンジン・話者）に差し替えられるようにするため。** 独立していれば、エンジンのイメージを差し替える・別ホストの既存エンジンを指す・話者を変える、のいずれも **agent を触らずに values・環境変数・設定ファイルだけで完結する**。

サイドカーにすると agent の更新のたびにエンジンも巻き直り、逆にエンジンを差し替えるたびに agent が落ちる。**両者のライフサイクルを結び付ける理由が無い。**

**捨てたもの**: サイドカー構成。localhost で済むネットワークの単純さより、差し替えやすさを取る。

**yachi8000 が依存してよいのは接続情報だけ**であり、エンジンが同じ Pod に居ることも、同じチャートでデプロイされていることも前提にしてはならない。

**⚠ 依存する API の契約を明示すること**: yachi8000 は音声合成に加えて **`/audio_query` 相当（モーラ単位の音素と長さ）をリップシンクに使う想定**（F-21、Q-07）。したがって差し替え先は「何らかの TTS」ではなく **VOICEVOX 互換 API を持つエンジン**でなければならない。**この契約を設定項目の説明に書き、満たさないエンジンを指したときは起動時に落とす**（黙ってリップシンクだけ壊れる、が最悪の壊れ方）。

### D-06. 外部通知 API を本体に持ち、割り込み発話として読み上げる

**決定**: `discord-vc` プラグインのバックエンド機能（HTTP で通知を受けて VC で読み上げる）を yachi8000 本体に取り込む。送信元と本文を LLM で自然文に書き換えてから読み上げる（F-15〜F-19）。

**理由**: Claude Code の作業完了通知はユースケースの一つに過ぎず、汎用の「外部から声を届ける入口」として持つほうが素直。書き換えを挟むのは、機械的な通知文をそのまま読み上げると会話の流れから浮くため。

**既存実装からの差分（重要）**:

| 論点 | discord-vc | yachi8000 |
|---|---|---|
| 認証 | `127.0.0.1` バインドのみ（到達性で防御） | **トークン認証必須。**k8s では到達性の防御が成立しない（F-18） |
| 再生順序 | FIFO キューのみ、割り込み無し | **優先度付きキュー**（F-17, INV-5） |
| 文面 | 受け取った文をそのまま合成 | 送信元 + 本文を LLM で自然文に書き換え（F-16） |
| 本文の扱い | 単なる文字列 | **非信頼データ**として LLM に渡す（F-19, INV-4） |

**書き換え失敗時の扱い**: 決定的テンプレート（送信元 + 本文をそのまま）で読み上げ、**WARN でログに残す**。これは house rule のフォールバック禁止の例外「意図的な部分縮退」にあたる。黙って隠さないことが条件（INV-7）。

### D-07. スキル自己改善は「生成は自動・有効化は承認制」

**決定**: 先行実装の `SkillCurator` 構成を踏襲する。返信確定後の fire-and-forget、`skill-curator:<tenantId>` の明示的 prefix、pending → approved の承認フロー（C-07, F-40〜F-43）。

**理由**: 生成を自動にすることで「自分で覚える」体験は成立する。一方、無審査で応答に反映すると、誤った一般化が人格として固定される。house rule の「確信度の低い自動判断を、確信ありげに適用しない」に直接あたる。承認を挟んでも自動生成の価値は失われない。

**捨てたもの**: 完全自動の有効化。**ただしこれは再検討の余地がある** — 承認が面倒で溜まるようなら、影響範囲の小さいスキルだけ自動有効化する案を Q-11 で扱う。

### D-08. リマインダーの文面は LLM に言い換えさせない（→ **D-30 で覆した**）

> **⚠ この決定は 2026-09-17 に D-30 で覆された。** 現在の方針は「保存した文面を素材にして LLM が伝える一言を組み立てる」。以下は覆される前の記録で、**実装の根拠として引かないこと。** 決定を消さずに残すのは、D-30 が何を引き受けたのか（＝下の理由が言う価値を、何と引き換えに手放したのか）を後から辿れるようにするため。

**決定**: リマインダーの発火時は、保存済みの title / description をそのまま読み上げる。

**理由**: 利用者自身が書いた文言の正確な再現に価値がある。先行実装でも同じ判断をしている。

**D-06 との違い**: 外部通知は「機械的な文を会話に馴染ませる」ことに価値があり、リマインダーは「書いたとおりに思い出させる」ことに価値がある。同じ読み上げでも扱いを分ける。

### D-09. Discord 連携は全て自前実装する

**決定**: Discord Gateway 接続・VC の参加/送受信・スラッシュコマンド・通知 API のエンドポイントを、infrastructure / interfaces 層に自前で実装する。

**理由**: `@flue/runtime` 2.0.3 の型定義を全文検索した結果、`discord` に一致する識別子・型・関数は**ゼロ**だった（C-10）。Flue が提供するのは汎用の HTTP ルーティング（`createChannelRouter()`、Hono ベース）のみ。

**帰結**: `discord.js` / `@discordjs/voice` を infrastructure 層で直接使う。**Q-04 はこの確認により解決。** Flue のバージョンを上げる際にアダプタが追加されていないかは、その都度確認すること。

### D-10. LLM は API キー方式のモデルのみを使う

**決定**: yachi8000 が使う LLM は、LLM プロキシの `model_list` のうち **API キーで認証するモデルに限定する。** OAuth トークン経由のモデル（Claude のサブスクリプション認証など）は使わない。

**理由**: LLM プロキシの OAuth 経路はホストの認証情報ファイルを bind mount して読む構成で、k8s では成立しない（C-05）。API キー方式に限れば、**キーを Sealed Secret に入れるだけで LLM プロキシをそのまま k8s に載せられる**。トークンの更新頻度という運用上の厄介も抱え込まずに済む。

**帰結**:
- k8s 上の LLM プロキシには認証情報ファイルの bind mount を持ち込まない
- `ccproxy.yaml` の `oat_sources` に依存する経路は yachi8000 のスコープ外
- **Q-01 はこの決定で解決。**

**捨てたもの**: OAuth 経由で使えるモデル。使いたくなった場合は、その時点で改めて k8s でのトークン供給方法を設計する。

### D-11. VOICEVOX は CPU 版イメージを使う

**決定**: `voicevox/voicevox_engine` の CPU 版イメージを、開発時（compose）・運用時（k8s Pod）ともに使う。GPU 版は使わない。

**理由**: 実測で RTF 0.14〜0.31、つまり実時間の 3〜7 倍速で合成できており、同時 2 リクエストでも破綻しなかった（C-14）。GPU を要求すると、ノード配置の制約・GPU リソースの奪い合い・イメージサイズの増加を抱え込むことになり、得られるものに見合わない。

**設計上の前提**: 実運用で効くのは合計時間ではなく初音レイテンシなので、**文単位で分割して合成し、1 文目が出来次第再生を始める**（C-15。一括 914ms → 分割 551ms）。この分割は D-05 の再生キュー（INV-5）の中に閉じ込め、呼び出し側に意識させない。

**再計測の条件**: 自宅 k8s ノードの CPU が開発機より大きく劣る場合は、デプロイ前に C-14 と同じ計測をやり直すこと。

### D-12. カスタマイズ設定は「静的設定」と「ランタイム状態」の二層に分ける

**決定**: ユーザー体験を決める設定を、書き手ごとに 2 つに分けて持つ。

| 層 | 中身 | 書き手 | 実体 |
|---|---|---|---|
| **静的設定** | 名前・既定の人格・口調・VRM の参照・話者 ID・固定モードの ON/OFF | **人の操作のみ**（手編集、または設定 UI での操作） | 設定ファイル |
| **ランタイム状態** | 会話で変化した人格の差分、学習したスキル、変化の履歴 | **プロセスのみ**（エージェント） | DB（SQLite） |

**応答時は「静的設定 + （固定モードでなければ）ランタイム状態の差分」を合成して人格を組み立てる。**

**理由**: house rule の「共有ファイルは静的設定とランタイム状態を分離する ── 混ぜると、一方のプロセスの停止処理が他方の設定を空にする」がそのまま当てはまる。人格が会話で変化する以上、**プロセスが人格を書き換える**。これを利用者が手編集するファイルと同じ場所に置くと、片方が片方を消す。

分けておくと副次的に次が成立する:

- **巻き戻しが引き算で済む**（F-33）。ランタイム状態を捨てれば既定の人格に戻る
- **固定モードが「差分を適用しない」だけで実装できる**（F-34）
- 設定 UI と手編集が**同じ実体**を触るので、「UI で変えたのに設定ファイルには無い」が起きない（F-61）

**「エージェントは書かない」の正確な意味**: 禁じるのは**会話ロジック**（エージェント・スキル・ツール・poller・停止処理・定期処理）からの書き込み。設定 UI のハンドラは agent プロセス内で動くが、**書き込みの契機が人の操作**なので許す（→ INV-9）。house rule が防ごうとしている事故は「プロセスの停止処理が人の設定を空にする」ことであって、人の操作の中継ではない。

**捨てたもの**: 単一の設定ファイルにエージェントも書き込む案。実装は一見単純だが、上記 3 つがすべて壊れる。

### D-13. 人格・口調固定モードは「差分を適用しない + システムプロンプトでの指示」で実現する

**決定**: 設定で有効にできる固定モードを用意する。実装は 2 段構え。

1. **ランタイム状態の人格差分を応答に適用しない**（決定的な部分。実際の防御はここ）
2. **システムプロンプトの先頭に「人格・口調を変更しない」旨の指示を入れる**（補助）

スキル自己改善ループ自体は止めない。人格・口調に関わらないスキル（手順・知識）は通常どおり動く。

**理由**: 自己改善ループを持つ以上、人格は変化する。それを望まない場面のために逃げ道を用意しておく。一方で、**変化そのものを止めてしまうと自己改善ループの価値も消える**ため、「変化は記録し続けるが適用しない」形にする。固定モードを OFF に戻せば、記録済みの変化が再び効く。

**既知の限界**: システムプロンプトによる指示は LLM への**お願いであって強制ではない**。長い会話や強い誘導で口調が揺れる余地は残る。**この限界を承知の上でこの方式を採る**（オーナー判断、2026-09-11）。決定的な保証が要るようになったら、出力側での検査に踏み込むことになるが、現時点ではやらない。

### D-14. 永続化先は PVC 上のファイル。ConfigMap は使わない

**決定**: インフラ定義リポジトリにある先行実装の chart の構成を流用する（ベクタストアだけは Qdrant ではなく Postgres + pgvector → D-20）。

| 対象 | 開発時（compose） | 運用時（k8s） |
|---|---|---|
| SQLite（会話履歴・スキル・人格差分・リマインダー） | bind mount した `data/` | **PVC**を `/data` にマウント |
| **設定ファイル（静的設定）** | 同上。**エディタで直接編集できる** | 同じ PVC 上の別ファイル |
| VRM ファイル | 同上 | 同上（→ 置き場所の詳細は Q-14） |
| ベクタストア（**Postgres + pgvector**） | compose の `postgres` サービス（`pgvector/pgvector:0.8.6-pg18`） | **別 Deployment + Service + 専用 PVC**（→ D-20）。**既存の共用 Postgres には相乗りしない** |
| 音声バッファ・合成キャッシュ | tmpfs | **`emptyDir`（`sizeLimit` 付き）**。PVC には置かない（C-12） |

**設定ファイルに ConfigMap を使わない理由**: **設定 UI が書き込むから**（F-61）。ConfigMap はマウントすると読み取り専用で、仮に書けても Pod の再起動で元に戻る。**「UI で変えたのに再起動したら戻っていた」は最悪の壊れ方**で、利用者からは原因が見えない。

**この決定の帰結（運用上の注意）**:

- **PVC の中身は ArgoCD の管理外。** マニフェストを git push しても設定ファイルは復元されない。**クラスタを再構築した場合、設定ファイルと VRM は手で置き直す必要がある**（house rule「クラスタ管理外のリソースを把握する」）
- したがって **PVC はバックアップ対象**。人格・記憶・設定はここにしか無い
- 手編集は k8s 上では `kubectl exec` / `kubectl cp` が要る。**日常の変更手段は設定 UI であり、手編集は開発時の利便とレスキュー用**と位置づける

**捨てたもの**: 設定ファイルを ConfigMap で GitOps 管理する案。設定の変更履歴が git に残る利点はあるが、UI から変更できなくなり F-61 が成立しない。**変更履歴が要るなら、設定ファイル側にバージョンを持たせるほうが筋がよい**（人格の変化履歴 F-33 と同じ考え方）。

### D-15. 埋め込みは LLM プロキシ経由の `text-embedding-3-small` / 1536 次元

**決定**: 開発用の LLM プロキシの `model_list` に OpenAI の embedding モデルを追加し、yachi8000 はそこを経由して埋め込みを取る（オーナー判断、2026-09-11）。

- モデル: `text-embedding-3-small`
- **次元数: 1536（ネイティブ）**
- pgvector の列もこの次元で定義する（→ D-20）

**理由**: 開発用の LLM プロキシには既に `OPENAI_API_KEY` が登録されており、**追加は `model_list` の数行で済む**。これにより **D-03 の「LLM の入口は LLM プロキシ 1 本」が埋め込みでも保たれる**。個人利用規模の長期記憶に `-large`（3072 次元）は過剰。

**捨てたもの**:
- 先行実装と同じ Gemini（`gemini-embedding-001`）— LLM プロキシに `GEMINI_API_KEY` が無く、追加すると入口が 2 本になる
- 768 次元への縮約 — 先行実装のコレクションと揃える意味は無い（テナントもデータも別）

**注意（実装時）**:

- **次元数はコレクション作成時に固定され、後から変えるには作り直しになる。** 設定で可変にせず、コード上の定数として持ち、変えるときは移行手順とセットで変える

### D-19. 音声入力は A → B → C の順で進め、最終形は両対応

**決定**（2026-09-11、オーナー判断）: 音声入力の経路を次の順で実装する。

| 段 | 経路 | 位置づけ |
|---|---|---|
| **A** | Discord VC からの受信（`@discordjs/voice` の `VoiceReceiver`） | **最初に作る** |
| **B** | 自前 Web ページのマイク入力（`getUserMedia` → WebSocket） | **次に作る** |
| **C** | A と B の併用 | **最終形** |

**理由**: A は「VC に入って話す」という本来の体験に最も近く、既存の `discord-vc` プラグインに必要なパッケージが全て揃っている。一方で Discord が音声受信を公式にドキュメント化していない以上、**A だけに賭けると仕様変更で会話手段が丸ごと失われる。** B を持てば、Discord が壊れても使い続けられる。

**確認済みの前提**（`claude-plugins` の `discord-vc/bot/node_modules` を実見、2026-09-11）:
- `@discordjs/voice` 0.19.2 が `VoiceReceiver` / `AudioReceiveStream` / `EndBehaviorType` / `SSRCMap` を export
- `@discordjs/opus` 0.9.0（ネイティブ Opus デコーダ）、`prism-media` 1.3.5、`sodium-native` 4.3.3 も導入済み
- **話者分離は `VoiceReceiver.ssrcMap`（SSRC → ユーザー ID）で標準提供される。** 自前実装は不要
- README に `*Audio receive is not documented by Discord so stable support is not guaranteed` と明記されている。**bot トークンで正規に動くため INV-1 には抵触しない**（selfbot が必要な映像送信とは性質が違う）

### ⚠ C が最終形であることが A の設計を縛る

**A を「Discord から音声を受けて応答する機能」として作ってはならない。** B を足すときに作り直しになる。

最初から**音声入力を port として domain に定義し、application は port 越しにだけ触る**。A も B も infrastructure 層の実装の 1 つに過ぎない、という形にする。

- domain: `音声入力ソース` の port（発話区間の PCM と話者 ID を流す）
- application: 「発話を受けて応答を作る」ユースケース。**どこから来た音声かを知らない**
- infrastructure: `DiscordVoiceInput`（A）と `WebMicInput`（B）の 2 実装
- 合成ルート: 設定でどちらを（あるいは両方を）配線するか決める

**これは house rule の「下の層の都合を、上の層の規約にしない」がそのまま当てはまる場面。** Discord の SSRC も WebSocket のセッション ID も、infrastructure の入口で「話者 ID」に正規化する。

**リスクの見方が変わった点**: 以前は「A が通らなければ D-02 の見直し」と書いていたが、**B は元から作る予定になったので、A の失敗は計画の前倒しであって手戻りではない。** Q-03 の位置づけを下げる。

### D-20. ナレッジベースは専用 Postgres + pgvector。Qdrant は採らない

**決定**（2026-09-11、オーナー判断）: 長期記憶のベクタストアは **yachi8000 専用にデプロイする Postgres + pgvector**。イメージは `pgvector/pgvector:0.8.6-pg18`（実在するタグを Docker Hub で確認済み。Postgres の最新メジャーは 18）。

**選定を「先行実装がそうだったから」で決めなかった。** 2026 時点の各候補を調べ直した結果:

| 候補 | 現状 | 判断 |
|---|---|---|
| **pgvector** | **事実上の標準。** 数百万ベクトル未満なら専用ベクタ DB は不要というのが主流の評価 | **採用** |
| Qdrant | 小規模〜1000万で良好。先行実装リポジトリの chart に実装済みで流用は容易 | 不採用（下記） |
| sqlite-vec | **0.1.10-alpha.4。ストレージ形式の破壊的変更が予告されている** | **失格** |
| SQLite Vec1（公式） | **0.7 pre-release。"testing is insufficient" と明記** | **失格** |

**alpha の 2 つを落とした理由**: 追加インフラが 0 で済む魅力はあるが、**長期記憶の永続性がこのプロジェクトの中核価値**であり、ストレージ形式が壊れうる選択肢は取れない。

**Qdrant ではなく pgvector を選んだ理由**: 個人規模では性能差が問題にならず、**同じ Postgres が LiteLLM の仮想キーも賄える**（→ Q-21, Q-22 が同時に解消する）。運用するデータストアの種類を増やさない。

**既存の共用 Postgres には触らない。** インフラ定義リポジトリの `helm-charts/postgres` は **`postgres:12-alpine`（EOL 済み）** で、**他のアプリが相乗りしている**。ここに新しい参加者を足すのは house rule の「共有資源の規約は参加者が増えるたびに確認する」に照らして筋が悪く、アップグレードは既存 2 つの移行が先に必要になる。**yachi8000 は自前の Postgres を持つ。**

**帰結**:
- 埋め込みは 1536 次元（D-15）。pgvector の HNSW インデックスで問題なく扱える
- インフラ定義リポジトリの `helm-charts/yachi8000/` に **agent / 音声合成エンジン / Postgres の 3 Deployment** が並ぶ
- ~~テナント分離は**列で持つ**~~ → **D-35 で撤回。** 記憶はひとつの空間に持ち、分離のための列は置かない。代わりに `speaker_id` で「誰の話か」を持つ（→ F-05）

### D-21. フェーズ 1 の実装で確定したこと

**決定**（2026-09-11、実装しながら確定）。いずれも実機で動かして確かめた。

**1. 設定ファイルの形式は YAML。**
人格・口調は複数行の文章になるので、ヒアドキュメント（`|`）が書ける形式でないと編集がつらい。コメントで各項目の意味を添えられることも効く（設定ファイルは利用者が直接開く。→ F-60）。捨てたもの: JSON（複数行とコメントが書けない）、TOML（入れ子が深くなると読みにくい）。

**2. 会話の文脈の粒度はギルド単位。チャンネル単位にしない。**
`discord-guild-<guildId>` / `discord-dm-<userId>`。同じサーバで交わした話を別チャンネルでも覚えていてほしいため。**当初は「テナント（記憶の分離単位）」と呼んでいたが、D-35 でテナント分離そのものをやめた。** 採番規則はそのままに、`ConversationId` として**短中期の会話文脈だけ**を分ける鍵になった —— この項の理由は文脈については今も正しい。区切り文字に `:` を使わないのは、Flue がエージェントインスタンス ID を会話読み取り URL の 1 パスセグメントに載せ、`:` を識別子の名前空間区切りとして予約しているから（`@flue/runtime` の `AGENT_IDENTITY_PATTERN` 周辺のコメントで確認）。

**3. モデルのメタデータは LLM プロキシの `/model/info` から起動時に取得する。**
`setProvider()` に渡す pi-ai の `Model` は `contextWindow` / `maxTokens` / 単価を必須で持ち、**`contextWindow` は Flue の自動圧縮（F-02）の閾値になる**。手書きのカタログに数字を並べると、モデルを足すたびに推測値が混ざり、圧縮が効かない・早すぎるといった形で会話が黙って壊れる。LiteLLM は実測値を返すので、それを起動時に読んで組み立てる。**`LLM_MODEL` がプロキシに無い、またはツール呼び出しに対応していない場合は起動を止める。**

**4. `auth` には `ProviderAuth`（`{ apiKey: envApiKeyAuth(...) }`）を渡す。**
`envApiKeyAuth()` の戻り値は `ApiKeyAuth` で、`CreateProviderOptions.auth` の型とは別物。直接渡すと型が合わない。

**5. 人格差分ストアは、差分を 1 件も返さない実装で先に配線しておく。**
差分の**記録**（F-33）はフェーズ 4 だが、**合成経路（静的設定 + 差分）と固定モードの分岐（F-34）はフェーズ 1 で通す**。後から合成を足す形にすると、固定モードが後付けの分岐になり「差分を読まない」という決定的な防御が抜ける。

**6. 長期記憶への書き込みは、ツール呼び出しだけを経路にする。**
先行実装リポジトリは毎ターンの発言を自動で RAG へ書いていたが、yachi8000 では踏襲しない。F-30 が求めているのは「明示的に記録された長期記憶」で、何でも溜めると想起が効かなくなる。

**7. 環境まわりで踏んだもの（再発防止のため記録）**:
- **npm は 11 以上が必要**（`npm install` の依存解決が npm 10 系の arborist のバグで落ちる。npm/cli#9787）。**`npm ci` は npm 10.9.8 でも通る**ため、ランタイムイメージ（`node:22-bookworm-slim`）の npm は据え置きでよい
- **pgvector の公式イメージ（PG18）は `/var/lib/postgresql` にマウントする。** `/var/lib/postgresql/data` へ直接マウントすると「unused mount/volume」と判断されて起動しない。**k8s の PVC でも同じマウント先にすること**
- **vite dev はコード変更時に SSR のモジュールグラフを丸ごと評価し直し、`import.meta.hot.dispose` は呼ばれない。** Discord Gateway の接続のようにモジュール再評価をまたいで生き続けるものは、`globalThis` に置いて明示的に閉じる。モジュールスコープの変数に持たせると二重ログインになる（実測で確認）
- **同一 Bot トークンで Gateway 接続は 2 本張れる**（Q-13 を実測で解決。当初の類推は誤り）。**繋がってしまうぶん危険で**、両方が同じイベントを受け取るため、気付かないうちに 1 通のメッセージへ 2 回返信する。プロセスを増やすときは「繋がるか」ではなく「**同じイベントを二重に処理しないか**」を問うこと

### D-22. 割り込み再生の方針と、フェーズ 2・3 の実装で確定したこと

**決定**（2026-09-11、実装しながら確定）。Q-05 / Q-06 をここで閉じる。

**1. 割り込みは「文の切れ目」で行う（Q-05 → (b)）。再生中の音声は切らない。**
発話は D-11 により文単位で分割合成されるので、(b) は「次の文を通知に譲る」だけで実現でき、追加の仕組みが要らない。(c)（即座に切る）を採ると VOICEVOX の `/cancellable_synthesis` が要り、**これは既定で無効で起動引数による有効化が必要**（C-16）。運用者が差し替えるエンジン（D-05）にその起動引数を要求することになるので、契約を増やさない (b) を採る。

緊急度をリクエストで指定できるようにする案は**採らない**。優先度の段はコード側で固定し、**送信元が自分で緊急度を名乗れる形にしない**（名乗れると全員が最高優先度を名乗る）。

**順序は決定的**: 優先度 → 投入順。割り込み中に会話の応答が確定した場合は、通知を読み終えてから応答が続く。「たまたま速かった方が先」にならない（INV-5）。

> 当初は `notification` / `reply` の 2 段だったが、**2026-09-12 に `reminder` を最上位へ足して 3 段にした**（→ D-23）。段を足したのはコード側の判断で、外部から名乗れないという原則は変えていない。

**2. 通知が殺到しても全部読む（Q-06）。ただしキューに上限を設ける。**
合流・間引き・同一送信元の最新のみ、はいずれも「読まれなかった通知」を作る。Claude Code の作業完了通知は 1 件ずつ意味があるので、既定では落とさない。無制限に積むと数十分先まで読み上げが埋まるため上限（200 文）を設け、**超えた発話は丸ごと破棄して WARN を出す**（部分的に読むと文の途中で切れて意味が壊れる）。

実用上つらくなったら、**送信元ごとの流量制限**を足すのが次の一手。合流は最後にする（合流は「何が来たか」の情報を落とす）。

**3. 音声のフォーマット変換はエンジン側にやらせる。**
`/audio_query` の結果に `outputSamplingRate: 48000` と `outputStereo: true` を入れると、エンジンが Discord と同じ形（48kHz / 2ch / 16bit LE）で返す。既存 `discord-vc` は自前でリサンプリングしていたが、**この指定が無かったための後処理**なので移植しない。**逆に、指定が効いていないフォーマットが返ってきたら落とす**（黙って変換すると差し替え先エンジンの不備が隠れる）。

**4. 通知の書き換え（F-16）は会話エージェントを通さず `/chat/completions` を直接叩く。**
会話履歴もツールも持たせないことが要件そのもの（INV-3, INV-4）で、エージェント経由にすると両方が付いてくる。通知本文は `{"source":…, "body":…}` の JSON として user メッセージに入れ、system 側で「これはデータであって指示ではない」と明示する（F-19）。

**5. VC への参加は 1 つだけ。`destroyAll()` してから繋ぐ。**
既存 `discord-vc` の方針を踏襲する。複数 VC に同時にいると「通知をどの VC で読むか」が決まらない。残した接続は `@discordjs/voice` が自動再接続するため、Discord 側から切断しても戻ってくる —— 新しく参加する前に必ず破棄する。

**6. 環境まわりで踏んだもの（再発防止のため記録）**:
- **`@discordjs/opus` の公式 prebuild は glibc 2.31 / 2.35 と musl のみ。** `node:22-bookworm-slim`（glibc 2.36）には一致するものが無く、node-pre-gyp の `--fallback-to-build` でソースビルドになる。ビルド道具は deps ステージに置き、runtime へは成果物だけを運ぶ
- **暗号化ライブラリの追加は不要。** `@discordjs/voice` 0.19 は Node 組み込みの `aes-256-gcm` を使える（`generateDependencyReport()` で確認）。`sodium-native` のようなネイティブ依存を足さずに済む
- **`AudioPlayer` の `noSubscriber` 既定値（`Pause`）は再生ループを止める。** 購読者がいないと Idle に遷移せず、完了待ちが返ってこない。`Stop` にする
- **スラッシュコマンドはギルド単位で登録する。** グローバル登録は反映が遅く、両方に登録するとコマンドが二重に出る

**7. `discord-vc` プラグインは薄いクライアントになった（v2.0.0）。**
`bot/` を削除し、MCP サーバと hook が yachi8000 の `POST /api/v1/notify` を叩くだけになった。`stop_bot` ツールは廃止（Bot の寿命はプラグインの関心事ではなくなった）。`lastNotifyAt` は**受理**時刻で返す —— 再生完了時刻にすると、長い応答の後ろにキューイングされている間に hook が「まだ鳴っていない」と誤判定して二重に鳴る。逆に、**破棄した通知では更新しない**（VC 未接続で捨てた直後にユーザーが VC へ入ると、hook が「もう鳴らした」と誤判定してそのターンだけ無音になる）。

### D-23. リマインダーはフェーズ 3.5 として実装する。発火は at-most-once

**決定**（2026-09-12、オーナー指示「フェーズ 3.5 にしつつフェーズ 3.5, 4 の実装をして欲しい」）。

**1. F-31 はフェーズ表から漏れていた。後回しにした決定は存在しない。**
`01-overview.md` の順序表には F-31 がどの行にも無く、`03-functional.md` では 1 行の要約だけだった。スコープ（利用シーン 3、「リマインダー・簡単な日常タスク」）には最初から入っており、**外すと決めた記録がどこにもない** —— つまり意図的な先送りではなく抜けである。フェーズ 3.5 として挿入し、この漏れ自体を記録する。

**整数で振り直さない。** Q-10 や `06-open-questions.md` が既存の「順 4 / 6 / 7」を名前として参照しており、番号を動かすと**参照側が黙って壊れる**。小数点の見栄えより、既存の参照が壊れないことを採る。

**教訓として**: 以後、要件をスコープに書いたらフェーズ表の行にも必ず現れること。フェーズに置かないなら、**置かない理由を書く**（F-36 がその形）。

**2. 発火は at-most-once。発火済みの印を届ける前に立てる。**
`UPDATE … WHERE id = ? AND fired_at IS NULL` で印を立て、変更行数が 1 のものだけを配信する。送信に失敗しても**再試行しない**（ERROR でログに残す）。

at-least-once（届いてから印を立てる）を採らない理由: 失敗の大半は「チャンネルが消えた」「権限が無い」のような**再試行しても直らないもの**で、その場合は再試行が延々と読み上げを試み続ける。そして**同じリマインダーを二度読み上げるのは、ログに残る 1 回の取りこぼしより悪い**（声は消せない）。

**3. 期限切れは捨てず、次のポーリングでまとめて発火する。**
Pod 再起動や更新で止まっていた間に過ぎた期限は、起動後の最初のポーリングで届く。「古いから捨てる」は**利用者が書いた予定を黙って消すこと**にあたる（INV-7 の趣旨）。時刻が過ぎていることは文面から分かる。

**4. 発話優先度は `reminder` > `notification` > `reply` の 3 段。**
リマインダーを最上位に置くのは、**期限に意味がある**唯一の発話だから。通知は「いつ読まれても内容は同じ」だが、リマインダーは遅れると価値が落ちる。

**5. 発火は「登録されたチャンネルへのテキスト送信」を常に行い、VC はそれに加算する。**
通知（F-15）ではテキスト配信は VC 未接続時の**縮退**だが、リマインダーでは**常の経路**。声は流れて消えるので、後から見返せる場所に必ず残す。VC で読むのは**同じサーバに接続しているときだけ** —— 別サーバの VC にいるときに読み上げると、関係のない人へ予定の内容が漏れる。

**6. 日時は日本時間の `YYYY-MM-DDTHH:mm` で受け、絶対時刻に解決してから保存する。**
相対表現を解く（「明日の 10 時」→ 具体的な日時）のは LLM の仕事（INV-3 の「判断」に収まる）。**保存されるのは解決済みの絶対時刻**で、「いつ鳴るか」を後の解釈に委ねない。**存在しない日時（`2026-02-31`、25 時）と過去は拒否する** —— `Date` は黙って繰り上げるため、指定した覚えのない時刻に鳴る事故になる。

### D-24. ランタイム状態の SQLite は、Flue の会話履歴 DB とは別ファイルにする

**決定**（2026-09-12）。

リマインダー・スキル・人格差分は `APP_DB_PATH` の SQLite に置き、Flue が使う `FLUE_DB_PATH` とは**別ファイル**にする。同じ PVC 上に 2 ファイルが並ぶ形。

**同居させない理由**: Flue の DB は**スキーマも圧縮もマイグレーションも Flue が所有する**。同じファイルに自分のテーブルを置くと、フレームワークの更新でどう扱われるか保証がない（少なくとも約束されていない）。壊れ方は「会話履歴が壊れる」か「リマインダーが消える」で、どちらも黙って起きうる。**ファイルを分けるコストは環境変数 1 本**なので、比べる必要がない。

**ドライバは `node:sqlite`（`DatabaseSync`）を使う。** Flue が内部で使っているものと同じで、**依存パッケージを 1 つも増やさない**。Node 22.21 ではフラグ無しで動く（実験的機能の警告のみ）。`npm install` が npm 10 系で落ちる問題（D-21 の 7）を抱えている状況では、依存を足さずに済むことの価値が大きい。

**⚠ 運用上の落とし穴**: `APP_DB_PATH` の既定値はコンテナ内の相対パス。**values で PVC 上のパスを渡し忘れると、リマインダー・スキル・人格差分が Pod 再起動ごとに黙って消える。** 会話は普通に続くので気付きにくい。手順は `docs/setup/deploy.md`。

### D-25. 通知 API に任意の `role` を足す。送信元とは別物として表示する

**決定**（2026-09-12、オーナー指示「突然『おわりました』みたいなこと言われても時間が経ったり並列で動かしてるとなにが終わったのかわからない」）。

`POST /api/v1/notify` の本文に任意の `role` を受ける（`{"text": "…", "role": "CI を直している人"}`）。書き換え（F-16）では**必ず文面に織り込み**、書き換えが落ちた縮退テンプレートにも出す。

**なぜ本文で受けるのか（トークンで決めないのか）**: 送信元（`claude-code`）は**誰が**を指すのでトークンから決まるが、`role` は**そのとき何をしているか**を指す。同じ送信元が並行して複数の作業を回すのが前提なので、**トークンに紐付けると役割の数だけトークンを発行する**ことになる。それは認証の話ではない。

**代わりに、騙れる値であることを隠さない**: `role` は自己申告で検証しない。読み上げ・表示では `送信元（role）` の形にし、**トークン由来（騙れない）と本文由来（騙れる）を同じ見え方で混ぜない**。混ぜると、認証して送信元を確定させている意味が薄れる。

**波及**: `discord-vc` プラグイン（別リポジトリ）が `role` を送るようになるまで、この項目は空のまま動く（任意項目なので互換は壊れない）。プラグイン側の対応は別作業。

### D-26. スキルは `pending → approved → disabled` の状態機械。承認はサーバ管理権限に限る

**決定**（2026-09-12）。Q-16 をここで閉じる（**実装時の判断であり、運用して成立しなければ見直す**。Q-11 と同じ扱い）。

**1. 状態遷移は必ず「現在の状態」を条件にする。**
`pending → approved`・`pending → rejected`・`approved → disabled`・`disabled → approved` の 4 遷移だけを許し、SQL は常に遷移元の状態を `WHERE` に含める。キュレーターの提案は fire-and-forget で非同期に届くため（F-40）、条件を付けないと**後から来た提案が承認済みの行を pending へ巻き戻す**。無効化からの再承認を許すのは、「効かなくなった」判断が誤りだったときに捨てずに戻せるようにするため。

**2. 承認・却下・無効化はサーバ管理権限（`ManageGuild`）を持つ人だけ。**
絶対ルール 4（自動生成されたスキルを無審査で有効化しない）が要求しているのは審査であって、**誰でも押せるボタンは審査ではない**。Discord の `setDefaultMemberPermissions` で宣言し、コード側の判定に頼らない（サーバ管理者が意図的に緩めることは許す —— それは運用者の判断）。

**⚠ 既知の穴だったもの → D-35 で消滅**: 以前はスラッシュコマンドがギルドで実行されると**そのギルドのテナント**を指したため、**DM テナントの pending に誰も手が届かなかった**（F-43 が DM では成立していなかった）。**D-35 でスキルの入れ物がひとつになったので、どのギルドのコマンドからでも触れる。** 代わりに**及ぶ範囲が全体になった** —— どのサーバの管理者が承認しても全員に効く。権限の根拠（`ManageGuild`）は変えていないが、**押した人のサーバだけに効くのではない**ことは運用上の前提として押さえておく。

**3. スキル候補は種別（`knowledge` / `persona`）を伴って提案される。**
Q-16 の問いは「固定モード中に、人格に関わるスキルをどう扱うか」だった。**分類を提案時に構造化して持たせる**ことで解く。固定モード中は `persona` 種別をマウントしない（F-34, F-42）。

これにより固定モードの規則が**一本に揃う**: 「人格に関わるものを読まない」。差分（D-13）とスキルが同じ規則で扱われる。**判断に迷ったら `persona` を選ぶ**ようキュレーターに指示する —— 知識スキルが固定モード中に効かないのは惜しいだけだが、人格スキルが効いてしまうのは**モードが壊れている**ことになる。

**分類を LLM に委ねている点が弱点**であることは認める。確実にしたいなら「固定モード中はスキルを一切マウントしない」だが、それは絶対ルール 4 が守ろうとしている価値（学習が効くこと）を固定モードが丸ごと潰すことになる。

**4. キュレーターのインスタンス ID は `skill-curator-<conversationId>`。**（D-35 以前は `<tenantId>`。採番規則は同じ値）
先行実装（C-07）は `:` 区切りだったが、`:` は Flue の識別子で名前空間の区切りとして予約されているため `-` を使う。**先行実装からの意図的な逸脱として記録しておく**（流用元と違うのは理由があるからだ、と後から分かるように）。

### D-27. Web 検索は Brave Search API を使う。キー不要の DuckDuckGo は使えない

**決定**（2026-09-12、オーナー指示「DuckDuckGo mcp 的なあれで web 検索も出来るようにしておいてほしい」→ 実測を示した上で Brave を選択）。

**1. キー不要の DuckDuckGo 経路は実測で使えなかった。**

| 経路 | 実測結果 |
|---|---|
| `html.duckduckgo.com` / `lite.duckduckgo.com` | **HTTP 202 + 結果ブロック 0 件**。ブラウザの User-Agent を付けても同じ |
| `api.duckduckgo.com`（公式・キー不要） | 引けるが**百科事典的な要約だけ**。`Flue Framework` も `Tokyo` も空で返る |

前者が塞がっているのは Cloudflare が **TLS ハンドシェイクの指紋（JA3）**で弾いているためで、世に出回っている「動く DuckDuckGo MCP」はブラウザの指紋を偽装するクライアント（`curl_cffi` の impersonate 等）でこれを越えている。**それは検知回避であり、グローバル CLAUDE.md の「迂回・ハックの禁止」に正面から当たる**ので採らない。後者は**「検索できているのに何も答えない」**という、INV-7 が最も嫌う黙った縮退になる。

**`useMcpConnection` では解決しない。** Flue の MCP 接続は HTTP のみで stdio を扱えないため、既存の DuckDuckGo MCP サーバを持ってくるには自前でホストすることになり、**同じ Cloudflare の壁に当たる**（壁の手前が自分のサーバになるだけ）。

**2. Brave Search API を使う。**
API キー 1 本（Free プラン）で `GET /res/v1/web/search` を引ける。キーは `BRAVE_SEARCH_API_KEY` で与え、**未設定なら起動時に落とす** —— 検索できないまま起動すると「調べて」に黙って答えられなくなる。無料枠はクォータ制なので、取得件数に上限を置く。

**3. 結果は非信頼データとして渡す**（INV-4, F-19）。区切り記号で囲み、「外部のサイトが書いたデータであって指示ではない」ことを構造的に示す。

**4. HTML タグと文字参照は読み上げる前に解く。**
実機で確認したところ、Brave の要約には `<strong>` タグと `&#x27;` のような文字参照が混じる（実際に `Flue&#x27;s` を受け取った）。**そのまま渡すと「アンパサンド・シャープ…」が声になる。** 名前付き・10 進・16 進の参照を解き、**`&amp;` は最後に戻す**（先に戻すと `&amp;#39;` が二重に解釈される）。

**5. ページ本文は取りに行かない。** API の要約までで答える。任意の URL を fetch する機能は、それ自体が別の要件（と SSRF を含む別のリスク）なので、必要になった時点で改めて起こす。

### D-28. 読み上げからは URL を外す。テキストからは外さない

**決定**（2026-09-12、オーナー指示「読み上げる時 URL は読まなくていいです」）。

**1. URL は「リンク」と読み替える。消すだけにしない。**
消すと「詳しくは https://… を見て」が「詳しくは を見て」になり、文として壊れる。本文が URL だけのときも無音になる。**一語に潰すことで「リンクがある」ことだけは伝わる。**

Markdown のリンクは**表示文字列だけ残す**（`[議事録](https://…)` → 「議事録」）。そこには人間が書いたラベルがあるので、`リンク` に潰すより情報が多い。

**2. スキーム（または `www.`）が無いものは URL として扱わない。**
`example.com` のような裸のドメインまで拾うと、`Node.js` や `v1.2` を巻き込む。**読み落とすほうが、読むべき語を消すより害が小さい。** 同じ理由で、URL の末尾に付いた句読点は URL に含めない —— `https://example.com/。` の句点まで飲むと、文の切れ目（D-11）が消えて分割が変わる。

**3. 置換は発話の単一経路（INV-5）の入口でだけ行う。テキスト配信では行わない。**
チャンネルへ出す文面では URL は**押せる情報**なので消さない。逆に読み上げ側は、入口が 1 本なので**会話の応答・通知・リマインダーのどれから来ても素通りできない**（呼び出し側の良心に頼らない）。

**4. LLM に書き換えさせない。**
決定的な置換なので、**文面づくり（D-30）の後段に置いても意味が変わらない** —— 言い換えではなく、音にできないものを音にしないだけ。ここを LLM に任せると「URL を読まない」が確率的になり、**指示を無視した回だけ「エイチティーティーピーコロン…」が声になる。** 置換は発話の単一経路の入口に閉じたままにする。

### D-29. 繰り返しのリマインダーは規則を保存する。毎日と毎週だけを持つ

**決定**（2026-09-16、オーナー指示「リマインダー機能に定期リマインド機能ほしいです。毎週火曜に〇〇みたいな」）。

**1. 保存するのは規則で、`due_at` は「次に鳴る時刻」。**
`{ kind: 'daily' | 'weekly', weekdays, time }`（時刻は JST の `HH:mm`）を行に持ち、発火のたびに次回へ進める。**D-23 の 6「いつ鳴るかを後の解釈に委ねない」と矛盾しない** —— 解決するのは `domain/reminder.ts` の `nextOccurrence`（純関数）で、**LLM は規則を組み立てるところまでしか触らない**（INV-3）。委ねたくなかったのは「実行時に自然文を読み直すこと」であって、決定的な計算ではない。

規則を保存せず、発火のたびに次回を 1 件登録し直す形は採らない。**登録し直しに失敗した瞬間に、以後の回が全部消える** —— しかも消えたことは誰にも分からない。

**2. 繰り返しの行は消えない。`fired_at` は永久に NULL。**
1 回限りは `fired_at` を立てて退場するが、繰り返しは `UPDATE … SET due_at = ? WHERE id = ? AND due_at = ? AND fired_at IS NULL` で次回へ進む。**`due_at` の一致が取り合いの印**で、1 回限りの `fired_at IS NULL` と同じ役割を果たす（D-23 の 2 の at-most-once はそのまま成立する）。`fired_at` を「最後に鳴った時刻」に転用しない —— 一覧・削除・ポーリングの 3 箇所で「まだ生きているか」の述語として引かれている列で、意味を足すと 3 箇所が同時に壊れる。

**3. 止まっていた間に過ぎた回は、まとめず 1 回に畳む。D-23 の 3 とは逆にする。**
1 回限りでは期限切れを捨てない（利用者が書いた予定を黙って消すことになる）。繰り返しでは逆で、3 日止まっていた毎日のリマインダーが**復帰時に 3 回鳴る**ほうが実害が大きい —— 同じ文面が連続で読み上げられ、内容は 1 回分の情報しかない。進める先は常に「復帰時点の次の回」。

**これは意図的な部分縮退なので、畳んだときは WARN で残す**（INV-7）。判定は「発火した回の次の回が、既に `now` 以前か」で見る。

**4. 毎月は持たない。毎日と毎週だけ。**
29〜31 日の扱いに決着が要るため（→ Q-25）。**曜日と時刻だけなら、存在しない日時が原理的に生まれない。** 頼まれたときに黙って近い日へ寄せるのは、D-23 の 6 が拒んだ「指定した覚えのない時刻に鳴る」そのものなので、対応しないことをツールの説明文に書いて言い換えを促す。

**5. ツールは `schedule_reminder` と分ける。**
入力が違う（絶対日時 ⇔ 曜日 + 時刻）。1 つのツールに `repeat` を足すと `due_at` の意味が分岐し、モデルから見て「繰り返しのとき due_at に何を入れるのか」が曖昧になる。**互換のための分岐ではなく、別の操作だから別のツール。**

**6. 既存の DB には列を後から足す。**
`CREATE TABLE IF NOT EXISTS` は既にあるテーブルに列を足さないため、PVC 上の DB では `prepare` が**起動時に**落ちる。`PRAGMA table_info` を引いて無いときだけ `ALTER TABLE … ADD COLUMN` する（SQLite に `ADD COLUMN IF NOT EXISTS` は無い）。「重複列」のエラーを握り潰す形にはしない —— 別の理由で失敗したときに気付けなくなる。

### D-30. リマインダーの文面は、保存したものを素材に LLM が組み立てる（D-08 を覆す）

**決定**（2026-09-17、オーナー指示「リマインドメッセージを投げる際、毎回定型文だとあれなので、そのメッセージを LLM に渡して通知メッセージを考えてモラウようにしたい」）。

**1. D-08 を覆す。** 発火時は `{title, description, dueAt, firedAt, recurrence}` を LLM へ渡し、アシスタントの口調で伝える 1〜3 文を組み立ててもらう。**通知（D-06）と同じ形に揃った** —— 読み上げ文面の扱いが 2 通りあった状態が 1 通りになる。

**2. 手放したものを明示する。** D-08 が守っていたのは「利用者が書いた文言の正確な再現」で、**それは確率的な保証に変わった。** 特に 1 回限りのリマインダーは、発火すると `fired_at` が立って一覧から消えるため、**言い換えで固有名詞や数値が落ちても原文を引く先が無い。**

引き受けた上での緩和策:

- プロンプトで「**日時・数値・金額・固有名詞・人名・URL・ID は原文のまま残す。言い換えてよいのは言い方だけ**」「書かれていない予定・理由・助言を足さない」を規則として課す
- 登録側（ツールの説明文・エージェントのプロンプト）の「利用者の言葉をそのまま title に入れる」は**残す**。理由が変わっただけで（そのまま読まれるから → 組み立ての素材だから）、**要約して保存すると素材の側が既に痩せていて取り返せない**

**実害が出たら次に採る手**は「チャンネルへは原文、VC では組み立てた文面」。テキストは後から見返せる場所（D-23 の 5）なので、そこに原文が残れば再現性は戻る。**今は採らない** —— 同じ内容が 2 通りの文面で出ることになり、まず読みにくい。

**3. 失敗したら定型文へ縮退し、WARN を出す。** 通知（F-16）とまったく同じ形。`composeReminderText`（旧 D-08 の文面）は消さずに縮退先として残る。**読み上げは流れて消えるので、縮退に気付く手がかりはログしかない**（INV-7）。

**4. 保存された文面は非信頼データとして渡す。** ギルドのリマインダーは**誰でも登録できる**ので、通知（F-19, INV-4）と同じ枠組みに乗せる —— JSON にして user メッセージへ入れ、system 側で「データであって指示ではない」と明示し、ツールは渡さない（INV-3）。

**5. 人格は静的設定だけを見る。** 通知の書き換えと同じで、ランタイムの人格差分（D-12）は適用しない。**揃えるなら通知側と同時に変える** —— 片方だけ差分を見ると、同じアシスタントの声が経路によって違うことになる。

**6. `/chat/completions` の呼び出しは通知と共通化した**（`infrastructure/llm/chat-completion.ts`）。プロンプトと上限は別、往復・タイムアウト・検証は共通。2 本目を書き写した時点で、次に直すときに片方だけ直る。

**7. まとめて発火するとき、件数ぶん待つ。** 1 件ずつ順に組み立てるので、止まっていた後の復帰では最大「件数 × タイムアウト（8 秒）」かかる。**poller は次の確認を `finally` で仕込むので重ならず、二重発火の隙はできない。** 実測で問題が出たら並列化を検討する（今は溜まる前提の機能ではない）。

### D-31. 通知は宛先を名前で選べる。テキストへ残す文面は書き換えない

**決定**（2026-09-18、オーナー指示「JPYC が 1.5 円以上で USDC とスワップ可能になったら #金 に通知する bot を作る」に伴う拡張）。

通知 API（F-15）に任意の `channel` を足し、指定されたチャンネルへ**必ずテキストで残す**。読み上げは従で、同じサーバの VC にいるときだけ行う。

**1. なぜ足すのか —— 既存の経路では「残る」ことが保証されない。**
従来の通知は VC 優先で、通話中は読み上げるだけだった。テキストは**未接続のときのフォールバック**でしかない。「価格が閾値を超えた」のような**後から見返す通知**は、たまたま通話中だったかどうかで記録が残ったり消えたりしてはいけない。

**2. 宛先は「名前」で受ける。チャンネル ID を本文で受けない。**
ID を受けると、**読み上げさせるために配ったトークンが「Bot の見えるどこへでも書ける」権限に化ける。** D-22 で緊急度を名乗らせなかったのと同じ理由 —— 送信元が自分で権限の範囲を広げられる形にしない。名前の解決先（`guildId` / `channelId`）は運用者が `notification.channels` に置く。

`role`（D-25）を本文で受けたのとは扱いが違う。`role` は**表示されるだけ**で権限を伴わないが、宛先は**配信先を決める**。騙れても表示が変わるだけの値と、騙れると届く先が変わる値を、同じ理由で扱わない。

**3. 設定に無い名前は 400 で弾き、既定の配信先へ回さない。**
名前を間違えた通知が**別のチャンネルへ出る**方が、届かないことより悪い（INV-7 の趣旨）。黙って倒すと、宛先を間違えたまま気付かずに流し続けることになる。

**4. テキストへ残す文面は LLM の書き換え（F-16）を通さない。**
書き換えは**読み上げを自然にするため**のもので、記録に残る数値や固有名詞を書き換えてよい理由にはならない。`1.502 円` が `だいたい 1.5 円くらい` になったら、その通知は用をなさない。**読み上げ文だけが書き換えの対象**で、チャンネルへは決定的テンプレート（`composeNotificationText`）をそのまま出す。

**これは D-30 の 2 で「実害が出たら次に採る手」と書いた「チャンネルへは原文、VC では組み立てた文面」そのもの。** あちらでは「同じ内容が 2 通りの文面で出て読みにくい」ことを理由に見送ったが、**通知では正確さの方が重い**ので採る。読みにくさは引き受ける。

**5. 従来の経路（`channel` なし）の書き換えも止めた。**
フォールバック配信は今まで書き換えた文面を出していたが、**読み上げないのに読み上げ用の文面を出す理由がない**。ついでに、テキストしか出さない通知では LLM を呼ばなくなる。

**6. 残っている不揃い**: リマインダー（D-30）は今もテキスト・VC の両方が組み立てた文面。**通知と規則が揃っていない。** リマインダーで固有名詞や数値が落ちる実害が出た時点で、こちらと同じ形へ寄せる。

**波及**: `notification.channels` は PVC 上の `settings.yaml` にあり、**ArgoCD の管理外**なので git push では置かれない（deploy.md）。money-topic 用のトークンを `NOTIFY_TOKENS` の Sealed Secret へ足す作業も併せて要る。

### D-33. 起票の道具はスレッドの中でだけ配る

**決定**（2026-09-18）。`create_github_issue` は、入口（`message-handler`）がスレッドの元投稿を読めたときにだけ `useTool` する。

### D-35. テナント分離をやめる。分けるのは会話の文脈と話者だけ

**決定**（2026-09-20、オーナー判断「1 つの人格として実装を進めたい。記憶の分離は不要」）。**ギルド / DM ごとのテナント分離（旧 F-04）を廃止する。** 人格・長期記憶・スキル・リマインダーは**全体でひとつ**。

**ただし複数人が話しかけてくる前提は変わらない。** Discord でも、将来の Web インターフェイスでも複数人が会話する。**分けたかったのは記憶の入れ物ではなく「誰の話か」だった**（→ F-05）。

**理由**: テナント分離は**先行実装から持ち込んだ構造で、このプロジェクトで要求された記録がどこにも無い**（`01-overview` に「先行実装と同様に持たせ」とあるのが唯一の出所）。実際に使っているのは 1 つの人格であり、サーバをまたぐと別人になる挙動は望んでいない。**持ち込んだ前提が要件でなかったと分かった時点で外す。**

**入れ替える軸**:

| 旧 | 新 | 何に使うか |
|---|---|---|
| `TenantId`（`discord-guild-<id>` / `discord-dm-<userId>`） | **`ConversationId`**（同じ値） | **Flue のエージェントインスタンス ID だけ。** 短中期の会話文脈を場ごとに分けるためのもので、記憶の分離には使わない |
| （無し） | **`SpeakerId`**（`discord-user-<id>`） | 長期記憶の帰属・プロフィールの鍵・リマインダーの登録者 |

**`ConversationId` の採番規則は変えない。** D-22 の 2（同じサーバで交わした話を別チャンネルでも覚えていてほしい）は**短中期の文脈については今も正しく**、鍵を変えると **PVC 上の会話履歴が全件迷子になる。** 名前だけを実態に合わせる。

**捨てたもの**: サーバごとに独立した人格・記憶・スキル。将来「このサーバでは別人格」が要るなら、そのときに改めて起こす —— **F-04 の番号は再利用しない**（意味を書き換えた要件として同じ番号に残す）。

**波及**:

- 各ストアから `tenant_id` を外す。`skills` の `UNIQUE (tenant_id, name)` は `UNIQUE (name)` になる
- **リマインダーの一覧・取り消しは登録者（`SpeakerId`）で絞る**（オーナー判断）。入れ物はひとつだが、他人の予定を消せる状態にはしない。未発火の上限も話者ごとに数える
- **スキルの承認はグローバルになる。** どのサーバの管理者が押しても全体に効く（D-26 の 2 の権限の根拠は変わらないが、及ぶ範囲が変わった）
- **Q-24（DM テナントのスキルに手が届かない）は消滅する。** pending が 1 つの入れ物に集まるので、どのギルドのコマンドからでも触れる
- **人格差分の及ぶ範囲が全体になる**（F-33 の既知の限界）。緩和は今までどおり事後 —— 一覧で気付き、戻し、必要なら固定モード（F-34）

**移行**:

- **会話履歴（`FLUE_DB_PATH`）は無傷。** インスタンス ID の採番規則を変えないため
- **長期記憶（pgvector）は列を落とすだけ**（`DROP COLUMN tenant_id`、インデックスは張り直し）。フェーズ 1 から積んだ記憶は残る。**ただし `speaker_id` には接頭辞を足す** —— テナント時代は Discord の生のスノーフレークを入れていたので、`discord-user-` を付けないと同じ人が 2 つの ID を持つ（F-05 の正規化）。件数は起動時に WARN で出す
- **ランタイム状態（`APP_DB_PATH`）はテーブルを作り直す**（オーナー判断で中身は捨てる）。SQLite は UNIQUE 制約に含まれる列を落とせず、フェーズ 3.5・4 は実機未確認でほぼ空のため。**リリース前なので、互換のための移行コードを残さない**

### D-36. アバターの置き場所と表情の扱い（Q-12 / Q-14 / Q-15 の決着）

**決定**（2026-09-20、アバターフェーズの着手時）。3 つまとめてここで閉じる。

**1. 表情は VRM 1.0 の標準プリセットだけを使う（→ Q-15）。**
`aa` `ih` `ou` `ee` `oh` `blink` `happy` `angry` `sad` `relaxed` `surprised` `neutral` `lookUp/Down/Left/Right`。**設定ファイルに対応表を持たない。**

three-vrm の `expressionManager` が、モデル固有の blendshape 名（例: `Face_Blendshape.Fcl_MTH_A`）をプリセット名の裏に隠す。**吸収する層が既にあるものを、こちら側で二重に持たない。** プリセットに無い表情が要るとなった時点で、改めて Q を起こす —— 先回りして対応表の仕組みだけ作らない。

**捨てたもの**: 設定ファイルに抽象名 → モデル固有名の対応表を持つ案（F-60 に追加する案）。モデルを差し替えるたびに人が表を書く運用になる。

**副産物**: VOICEVOX のモーラが返す母音 `a i u e o` が `aa ih ou ee oh` に 1 対 1 で対応する（→ Q-07 の残りのうち、マッピングの側はこれで済む。`speedScale` の伸縮は F-21 の実装時に実測する）。

**2. VRM は設定ファイルと同じ場所（PVC）に置き、agent が配信する（→ Q-14）。**
設定ファイルの `avatar.vrmPath` が指す 1 ファイルを読んで返す。

**設定ファイルと運用経路を揃える**のが理由 —— どちらも人が手で置き、ArgoCD の管理外で、クラスタ再構築時に置き直す対象で、バックアップ対象（`docs/setup/deploy.md`）。実体が 2 種類あるのに置き方が違うと、片方だけ忘れる。

**捨てたもの**: オブジェクトストレージ（運用する実体がもう 1 つ増える）、設定 UI からのアップロード（**F-61 の後でないと作れない**。先に置き場所だけ決める必要があった）。**UI からのアップロードは後から足せる** —— 置き場所が PVC なら、書き込む経路が増えるだけで読む側は変わらない。

**大きさの前提**: 開発の基準機が 10.7 MB。**初回ロードのキャッシュ戦略は持たない**（Q-14 が「要るかもしれない」と書いていたもの）。この大きさなら要らない。必要になるのは、モデルを差し替えて桁が変わったとき。

**3. 開発の基準機は three-vrm のサンプルを使う（→ Q-12）。**
`VRM1_Constraint_Twist_Sample.vrm`（pixiv Inc.、VRM 1.0、10.7 MB）。**ライセンスは推測ではなく、VRM に埋め込まれたメタを読んで確認した**（2026-09-20）:

| 項目 | 値 |
|---|---|
| `allowRedistribution` | `true` |
| `modification` | `allowModificationRedistribution` |
| `avatarPermission` | `everyone` |
| `creditNotation` | `unnecessary` |
| `commercialUsage` | `corporation` |

**プリセット表情が 18 個すべて入っている**ので、1 の決定がこのモデルで成立することは実測で確かめてある。

**リポジトリにはコミットしない**（→ F-62）。再配布は許されているが、**理由は容量のほう**（public リポジトリに 10.7 MB のバイナリを置かない）。取得手順は `docs/setup/avatar.md` に置き、**ブランチではなくコミット SHA で固定する** —— `dev` を指すと中身が黙って差し替わる。

**4. アバターの表示ページにも認証をかける**（2026-09-20、オーナー判断で当初の「かけない」から変更）。
**ビューアには発話テキストと会話状態が流れる**（F-21, F-22）ので、到達できる人には会話の中身が見える。絶対ルール 5（INV-6）が守っているのは「アシスタントに発話させられる入口」なのでビューアは厳密には当たらないが、**守るコストがほぼ無い**と分かったので守る側に倒した（→ D-37。ingress の設定を足すだけで、アプリ側には何も入らない）。

**当初は「かけない」と決めていた。** 変えた理由は方式が決まったことで、判断の中身が変わったわけではない —— 「読むだけのビューアは絶対ルール 5 の対象ではない」は今も正しい。

**5. `web/` の成果物は agent が配信する。**
同一オリジンにすることで、F-61 の設定 UI が API を叩くときに CORS の設計が要らなくなる。開発時は `web/` 側の Vite dev サーバを別に立て、API はそちらから agent へプロキシする。

### D-37. Web の認証は ingress で認証基盤に委ねる。アプリは OIDC クライアントにしない

**決定**（2026-09-20、オーナー判断）。`web/`（アバターのビューアと設定 UI）の認証は、**ingress の forward auth** で行う。クラスタには既に認証基盤（別リポジトリのインフラ定義にある）が載っている。

**yachi8000 側にはコードを入れない。** OIDC のライブラリもセッション管理もクライアントシークレットもリダイレクト URI も持たない。ingress の annotation（`auth-url` / `auth-signin` / `auth-response-headers`）だけで済む。

**理由**: 認証は既に運用している実体があり、そこへ寄せれば**守るべき秘密がアプリに 1 つも増えない**。ビューアと設定 UI を別々に守る必要もなくなる（同じ ingress の下にあるため）。

**捨てたもの**: yachi8000 自身を OIDC クライアントにする案。Pod へ直接来たリクエストまで守れるのが利点だが、そのために**セッション・cookie・クライアントシークレットをアプリが抱える**。今のところ Pod へ直接届くのはクラスタの中からだけで、そこまで塞ぐ必要が出ていない。**必要になったら移れる** —— ingress 側を外してアプリ側を足す形になり、逆順の移行より簡単。

**波及**:

- **通知 API の Bearer（F-18）はそのまま残す。** forward auth は ingress の外側で効くので、**クラスタ内から Pod へ直接来たリクエストには効かない。** 「アシスタントに発話させられる入口」は到達性に頼らない、という絶対ルール 5 は ingress では満たせない。**2 つは役割が違うので、両方持つ**
- **話者の判別に使える**（→ F-05）。forward auth は利用者を示すヘッダをアプリまで通すので、そこから `SpeakerId` を作れば「Web インターフェイスでは認証が話者判別の前提」が満たせる。**ただしヘッダは ingress が必ず上書きすることが前提** —— 外から偽装ヘッダを付けられる経路が 1 つでもあれば、名乗りを自己申告にしたのと同じになる。**配線時に実際に偽装を試して確かめること**
- **クラスタにはまだ forward auth を使っているアプリが 1 つも無い**（2026-09-20 時点でインフラ定義側に該当する annotation が無い）。outpost の配線はこれが最初になるので、**認証基盤側の作業が先に要る**

**配線の記録**（2026-09-20）。実際に載せたものと、途中で分かったこと:

- **認証基盤側が先**（そちらが無いと `/outpost.goauthentik.io/*` はどのプロバイダにも解決されず 404 になる）。proxy provider（`forward_single`）・application・**埋め込み outpost への紐づけ**を blueprint で宣言し、`authentik_host` も入れる（空だとブラウザ向けの認可 URL が localhost のまま組まれる）。**UI で作らない** —— 手で作ったオブジェクトは GitOps の管理外で、クラスタ再構築時に復元されない
- **`/outpost.goauthentik.io` を受ける Ingress は認証基盤の namespace に置く。** Ingress のバックエンドは同じ namespace の Service しか指せない。ingress-nginx は同じホストの Ingress を 1 つの server ブロックにまとめるので、TLS はアプリ側の Ingress が持っているものがそのまま効く
- **アプリ側の Ingress は 2 本に分ける。** annotation は Ingress 単位でしか効かない。`/` に forward auth を付け、**自前の Bearer 認証を持つ API と死活監視だけ**を別 Ingress で素通しにする。認証済みの呼び出しをログイン画面へ 302 すると、JSON を期待している呼び出し側が壊れる
- **`X-Forwarded-Host` を `auth-snippet` で渡す公式手順は、このクラスタでは通らない。** ingress-nginx が 2 つ動いていて（GitOps 管理のものと Kubernetes ディストリビューション同梱のもの）、**どちらも class `nginx` の Ingress を admission で検証する。** 後者は snippet を許可していないため、`*-snippet` を含む Ingress は拒否される。ConfigMap を指す `auth-proxy-set-headers` に替えた（値は nginx の設定へそのまま書き出されるので変数が使える）。**認証のサブリクエストでは `Host` が `auth-url` のホストに差し替わる**ため、この転送自体は省けない
- **順序を間違えた。** アバターをデプロイした時点（2026-09-20）で ingress は `/` を素通しで公開しており、**ビューアのページと `/api/v1/avatar/*` が認証なしでインターネットから見える状態が数時間続いた。** D-37 で「forward auth が前提」と書いておきながら、既存の ingress を確認せずにイメージを上げたため。**公開経路を持つアプリでは、機能より先に ingress を見る**
- **利用者を示すヘッダが信用できるのは、forward auth をかけた Ingress の下だけ**（→ F-05）。生成された nginx の設定を読んで確かめた: `/` の location には `auth_request_set $authHeaderN $upstream_http_x_authentik_*;` と `proxy_set_header 'X-authentik-*' $authHeaderN;` が並び、**client が付けてきた同名のヘッダは必ず上書きされる**。一方、**素通しにした path の location にはこの行が無い** —— そちらへ偽装ヘッダを付ければアプリまでそのまま届く。**`SpeakerId` をこのヘッダから作るなら、対象を forward auth の下の経路に限ること**


### D-38. 発話イベントは SSE で配る。リップシンクの長さは `speedScale` で割る（Q-07 の決着）

**決定**（2026-09-20、アバターのスライス 2 の着手時）。F-21 の「WebSocket」を **SSE（Server-Sent Events）** に改める。併せて Q-07 を閉じる。

**1. 転送は SSE。WebSocket は使わない。**

**理由は Flue の制約**（実装を読んで確認した）。`@flue/vite` の `startFlueNodeServer` が Node の http サーバを内側で作り、**呼び出し側へ返さない。** WebSocket を足すには `injectWebSocket(server)` に渡すサーバの実体が要るが、それが手に入らない。

残る手は「別ポートでもう 1 本サーバを立てる」か「Flue の起動経路を自前で書き直す」かで、前者は **ingress と forward auth（D-37）の対象が 2 つに増え**、後者はフレームワークの更新のたびに追従が要る。

**SSE は普通の Hono の Handler の中で完結する**（`ChannelRouteDefinition.handler` は Hono の `Handler` そのもの）。**発話イベントはサーバからブラウザへの一方向**なので、双方向である必要がそもそも無い。ブラウザ側は `EventSource` で、再接続は標準で付いてくる。

**捨てたもの**: 別ポートの WebSocket サーバ（ingress と認証の対象が増える）、Flue の bootstrap の置き換え（追従コストが恒久的に残る）、ポーリング（発話の粒度に対して間隔が粗すぎる）。

**2. リップシンクの長さは、モーラの長さを `speedScale` で割って作る（→ Q-07 の決着）。**

**実測**（2026-09-20、VOICEVOX 0.25.1。`/version` で確認）:

| `speedScale` | 合成された音の長さ | モーラ合計 + pre/post を `1/speedScale` した予想 |
|---|---|---|
| 1.0 | 2.9547s | 2.9619s |
| 1.5 | 1.9627s | 1.9746s |
| 2.0 | 1.4933s | 1.4809s |
| 0.5 | 5.9413s | 5.9237s |

- **`/audio_query` が返す長さは常に等倍。** クエリ文字列に `speedScale` を付けても**無視され**、返ってくる `speedScale` は `1.0` のまま、モーラの長さも変わらない
- **伸縮は `/synthesis` の側で起きる。** `prePhonemeLength` / `postPhonemeLength` を含め、**全体が一律に `1/speedScale` される**（ずれは 1% 未満。エンジン内部の丸めの範囲）
- したがって**口形の時刻は「モーラの長さ ÷ `speedScale`」で計算でき**、音量エンベロープを別途取る必要は無い

**母音から VRM プリセットへの対応**（実測した `vowel` の値。→ D-36 の 1）:

| `vowel` | 口形 |
|---|---|
| `a` `i` `u` `e` `o` | `aa` `ih` `ou` `ee` `oh` |
| `A` `I` `U` `E` `O`（無声化母音。`シャツ` の `ツ` など） | 同上（**声は出ないが口は動く**） |
| `N`（撥音）`cl`（促音）`pau`（句読点の間） | 口を閉じる |

**3. 出すのは「話している」だけ。**

F-22 の 4 状態のうち、スライス 2 で出すのは **`speaking`**（発話キューが持っている情報でそのまま出せる）。`thinking` は 1 ターンの実行から出せるので落ち穂拾いで足す。**`listening` は音声入力（フェーズ 7）が無いと出どころが無いので、そこまで持ち越す。**

**4. 既知の限界**:

- **Discord VC の再生とブラウザの受信にずれがある。** 音は VC 経由、イベントは HTTP 経由で、**この 2 つの遅延は揃わない。** スライス 2 では補正しない —— **補正すべき量は実機で測らないと分からない**（測らずに入れた補正は、ずれの向きを間違えると悪化する）
- **イベントは「再生を始める直前」に出す。** `play()` の内側に「音が鳴り始めた瞬間」を取れる場所は無い
- **このエンドポイントに認証は無い**（→ D-37 と同じ。守るのは ingress 側）。**発話させられる入口ではない**（読むだけ）ので、絶対ルール 5 の対象ではない
- **`pauseLengthScale` / `intonationScale` は既定値（1.0）のままで測った。** 合成側もこの 2 つは触らない。**設定ファイルから変えられるようにするなら、伸縮を測り直すこと** —— 前者は `pause_mora` の長さだけを動かすので、口形の時刻が句の切れ目からずれる

**5. 開いたままの SSE は停止をぶら下げる。停止処理で自分から打ち切る。**

**当初「止めない」と書いたが、誤りだった**（読んだのが起動側の `node-server.mjs` で、lease を取っているのは `createChannelRouter` の中だった）。`dispatchChannelRequest` はハンドラの前に `activityGate.enter()` を取り、**応答が流しっぱなしなら `retainActivityLease` で本文が終わるまで持ち続ける** —— コメントにも「graceful reload/drain waits for in-flight streams」とある。

SSE の本文は**ブラウザが閉じるまで終わらない**ので、ページを開いたままの人が 1 人いるだけで、停止が `server.mjs` のタイムアウト（60 秒）までぶら下がる。**更新戦略が `Recreate`** なので、デプロイのたびにその 60 秒が乗る。

**対処**: `SIGTERM` / `SIGINT` で**配る側から購読を打ち切る**（`closeAll()`）。ハンドラは「ブラウザが閉じた」と「こちらから打ち切った」の 2 つで終わる。ブラウザ側は `EventSource` が勝手に繋ぎ直すので、利用者からは新しい Pod に繋ぎ変わるだけに見える。

**教訓**: **フレームワークの挙動は、実際に通る層を読むこと。** 1 つ上の層を読んで「呼んでいない」と結論を出した。


### D-39. ブラウザでも音を鳴らす。口形はその音の再生位置で引く

**決定**（2026-09-20、オーナー判断）。アバターのページで、**Discord VC と同じ音を、加えて**鳴らせるようにする（→ F-23）。

**1. 出口が 2 つになるが、発話キューは 1 本のまま**（→ INV-5）。

**合成は 1 回。** ブラウザへ渡すのは Discord へ流したのと同じバイト列で、口形（F-21）も同じ合成から作る。**2 回合成したら経路が 2 本になったということ**で、そのときは順序も内容もずれる。

**2. 口形は「鳴っている音の再生位置」で引く。**

ブラウザで鳴らしているなら、その要素の再生位置が 0 秒。鳴らしていないなら、今までどおりイベントが届いた時刻が 0 秒。

**これで D-38 の 4 に書いたずれが、ブラウザの中では消える** —— 音と口が同じ時計を見るため。**Discord VC の音とのずれは残る**（別の出口なので）が、それは「VC で聞いている人」の話で、その人はアバターを見ていないことのほうが多い。

**3. 既定では鳴らさない。押したときだけ鳴る。**

理由が 2 つ重なっている:

- **VC にも入っている人は二重に聞く。** どちらを黙らせるかは人の都合なので、既定を「鳴らない」にして選ばせる
- **ブラウザは操作なしに音を出せない**（自動再生の制限）。押してもらう工程はどのみち要る

**捨てたもの**: 常に鳴らす（二重再生を手で消す運用が残る）、VC 接続の有無で自動で切り替える（**「VC にいるのが誰か」と「ブラウザを見ているのが誰か」は別人でありうる**ので、判定が当てにならない）。

**4. 音はイベントとは別に取りに行く。**

読み上げイベントには **ID だけ**を載せ、ブラウザが `GET /api/v1/avatar/speech?id=<id>` で WAV を取る。

**捨てたもの**: SSE に base64 で載せる案。サーバに状態を持たずに済むが、**3 秒の文で 700KB 級**になり、それが同じ接続を流れる後続の口形イベントを塞ぐ（口が遅れる）。

**ID はクエリで渡す**（`?id=<id>`）。**Flue のチャンネルルーターはパスを文字列一致で引く**ので、`/speech/:id` のようなパラメータは一生マッチしない（実機で 404 になって気付いた）。同じ理由で、**このルーターに載せるパスにパラメータを使わないこと。**

**5. 溜めるのは直近だけ。**

合成済みの音はメモリに置き、**古いものから捨てる**（上限は大きさと時間の両方）。PVC には置かない —— 発話の音は作り直せるうえ、残す価値が無い（音声バッファを永続ボリュームに置かない、という既存の方針と同じ）。**取りに行ったときに消えていたら、そのぶんは鳴らさず口だけ動かす**（WARN。→ INV-7）。

**6. このエンドポイントは会話の中身そのものを返す。**

口形イベント（D-38）が漏らすのは口の形だけだったが、**こちらは喋った内容が音として取れる。** ID を推測できない値にして寿命も短くするが、**実際の守りは ingress の認証**（→ D-37）であり、それ以上のものはアプリ側に持たない。**到達できる場所へ出すときは forward auth が先**、という D-37 の前提がここで効いてくる。

**発話させられる入口ではない**ので、絶対ルール 5（＝ INV-6）の対象ではない。通知 API の Bearer とは役割が違う。
